# 生码规则与示例

用于编码前的职责划分、设计选择，以及编码后的实际代码审查。规则适用于本次新增或修改的代码；当前用户要求决定任务范围，项目约定确定具体组织方式。发现历史惯例与当前要求不同，按本次明确要求实现并保留变化原因；业务含义仍有歧义时指出缺失信息，不自行补造规则。

## 编码前：项目依据与本次实现选择

本流程适用于各种代码生成与修改，不围绕特定请求库设规则。先读适用项目规范、相关实现与用法，结合本次要求和已核实历史，确定应沿用的职责边界、依赖与扩展方式、公共能力、注释和风格。候选清单只用于定位；必须阅读实际内容，未知处继续检索。

通过 `implementation_basis` 保存少量实际原文引用与具体实现选择，并关联到现有验收。每项选择说明约束和本次怎样落实：可以沿用已有实现、扩展既有能力或有理由地采用新方案；不照搬不适用的旧代码。默认五项规则按任务相关性纳入，无组件场景不补组件验收。

修改方案后保留依据历史、重开相关验收，收尾对照实际代码逐项检查。单独通过测试或引用一个文件不能证明模块化、模式或复用正确。MCP 校验引用、记录与当前验收关系；语义、设计取舍和偏离理由仍由执行者核实。

## 1. 按职责模块化

- 按业务职责、变化原因和依赖边界组织文件。业务计算、请求或存储访问、页面交互、跨模块通用工具需要清晰边界，禁止混入互不相关的函数。
- 同一职责的私有辅助函数可留在同一文件；组件自身的交互状态和模板也可沿用框架的共置方式。无需一函数一文件，不以行数决定拆分。
- 优先复用项目已有分层。旧文件职责混杂时，提取本次新增或直接涉及的独立职责并验证调用方，保留无关旧行为；不要借机重构全仓库。
- 依赖通过职责明确的入口衔接，避免循环依赖、绕过业务校验直接访问存储，或把业务专属函数塞入通用 `utils`。

示例：订单页面只负责展示和操作编排；金额计算可放到订单领域模块，请求放到项目既有服务层。金额计算内部的舍入辅助函数可以共置；它只有跨业务复用依据时才适合成为通用工具。

验收看实际职责与调用方向，不按文件数量评分。

## 2. 按实际问题选择设计模式

先判断当前是否有明确的可替换行为、复杂状态转换或外部接口差异，再选择项目中适用的实现方式。

| 当前问题 | 可考虑的方式 | 需要核对 |
| --- | --- | --- |
| 多种计价或校验算法可替换 | 策略模式；函数表也可实现 | 策略是否共享稳定输入输出，是否真的存在多种行为 |
| 状态转换有明确规则和操作限制 | 状态模式或显式转换表 | 状态与转换规则是否有需求或源码依据 |
| 不同外部服务字段与接口不一致 | 适配器模式 | 差异是否被限制在边界，调用方是否仍需了解外部细节 |
| 修改文案、补充简单判断或单个字段 | 现有函数或简单分支 | 是否可以用当前结构直接表达，无需新增抽象 |

说明“解决什么问题、为什么适合、有哪些成本”即可，不要求每次套模式。函数组合、数据表和现有框架机制都可用；没有复用或变化依据时，不为凑模式创建工厂、接口或多层继承。

## 3. 保留并核对用户要求

- 开始时记录需求和可观察的验收条件，区分本次要求、已确认项目规则、待核对的历史候选。
- 实施中新要求或纠正进入任务的 `corrections`，注明实际来源、原因与范围；同步维护关联清单和验收项。初始要求直接进入需求和验收，不伪造为纠正记录。
- 当前明确要求与旧要求不同时，保留变更原因并按当前要求验收。保留原有记录 ID；受影响的完成项重新进入待检查状态。字段映射见[任务输入说明](task-inputs.md)。
- 恢复任务先读保存的验收和纠正；新任务通过项目知识和历史查询获取相关线索，并核实适用条件。一次性文案要求、临时处理不自动成为全局惯例。
- 有复用价值的纠正可经 `experience_propose` 保存本地候选；团队确认规则仍走明确审查。候选、任务记录和共享规则是不同状态，不把保存记录表述为永久生效。

## 4. 配套清晰的注释

| 位置 | 注释内容 |
| --- | --- |
| 新增或职责发生变化的模块 | 模块职责、边界和必要的依赖约束 |
| 新增或契约发生变化的公共函数、方法 | 用途；不直观的参数含义、返回值、副作用和异常 |
| 关键业务判断、特殊兼容处理 | 业务依据、适用条件和为什么这样处理 |
| 不易直接看懂的实现 | 设计原因、算法限制或需要保留的约束 |

默认使用中文，沿用项目已有的 JSDoc、TSDoc 或其他注释格式。类型已经清楚表达的内容无需重复，简单私有辅助函数不逐行加注释。修正逻辑时同步修正或删除失效注释；描述真实行为，不写“以后处理”等无依据承诺。只维护本次涉及的代码，不改第三方或生成产物以满足注释要求。

例如金额边界处理应说明舍入的业务要求或已确认来源，而非仅写“进行四舍五入”；没有来源时明确待确认，不用注释补造业务结论。

## 5. 按优先级选择组件

顺序固定为：**项目已接入的组件库 → 项目已有可复用组件 → 自行实现**。

1. **检查组件库。** 核对项目当前安装版本及实际导出、类型、使用示例，评估属性、插槽和已有扩展能力。满足需求就使用；不能因为存在依赖声明而假定某 API 可用，也不因为优先查库就擅自引入新组件库。
2. **检查项目组件。** 组件库无法合理满足时，再检索项目的可复用实现，评估直接复用或合理扩展。修改共享组件需检查其他调用方和兼容性。
3. **自行实现。** 前两层均无法合理满足时，说明已检查的位置、具体缺口和自研边界，再新增组件。遵循职责划分、适当设计与注释要求。

“满足需求”同时包括功能、实际 API 和项目必要的权限、样式、交互等约束。库组件缺少项目必需能力，而现有封装已提供时，说明缺口后使用该封装，仍遵循上述顺序；未经核对的历史候选不能成为跳过组件库检查的理由。

不涉及组件的任务说明不适用即可，不要求前端目录、组件选型表或额外 UI 改动。

## 记录与交付

编码前用简短说明明确职责和选择，按[任务输入说明](task-inputs.md)写入现有任务字段；不新增自定义 MCP 参数。结束时对照实际差异检查适用规则，证据引用实际路径或验证结果，不只填写“已遵守规范”。

这些规则指导 Codex 的设计和审查。MCP 仅校验记录结构、来源和代码快照，无法独立判定模块化、模式、注释的合理性；仍需执行项目现有验证。
