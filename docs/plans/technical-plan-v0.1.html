Codex 项目开发 Agent：初步技术方案 v0.1

保留最初的设计依据与取舍，供回顾实现过程。

历史记录2026.10.13约 9 分钟阅读

历史设计记录。 以下保留制定时的内容和进度；当前安装与使用方式请以安装指南为准。

日期：2026-10-13。状态：方向已确定，进入任务拆分，尚未实现或验证。工具面向本地 Codex 与不同 Git 仓库，项目语言和框架作为接入信息配置。

实施启动方式：先独立开发通用工具包并使用小型 Git 样例验证，真实项目用于后续试用和效果评估，不是开始开发的前提。具体顺序见 实施计划 v0.1。

目标是减少三类人工纠偏：实现不符合项目惯例、遗漏业务约束、只改局部而遗漏关联位置。首版通过项目依据检索、结构化改动清单、逐项核对和经验复用改善开发过程，效果用真实任务验证。

1. 产品形态与首版范围

产品是 Codex 中的“项目开发”技能，后续将技能与本地工具配置打包为团队插件。同事通过 Codex 对话提出需求、纠正方案、查看结果，代码修改与验证沿用 Codex。

一次任务提供三种结果：开发前给出相关依据、业务待确认项和预计影响范围；完成后给出逐项核对结果、遗漏线索与验证记录；收到有价值的纠正后生成经验草稿，人工审查后进入共享知识。

首版限定一个仓库、一个模块或一类常见需求，例如“给现有接口增加行为或字段”。首版交付项目约定与经验检索、改动清单、完成核对、经验草稿和任务效果记录。多仓协作、独立管理网站、全仓调用图、向量数据库、自动确认经验和运行时强制门禁留作后续选择。

2. Codex 接入依据

Codex 可以使用项目级 AGENTS.md、显式调用 Skills，并连接本地 STDIO MCP 服务。这些是接入基础；本文的工具、数据结构和流程均为拟议设计。参考官方的 AGENTS.md、Skills 和 MCP 文档。

试点先使用仓库级 Skill 和本地 MCP 配置，验证接入与工作流；稳定后按官方 插件打包文档 通过团队或仓库 marketplace 分发。优先验证 Codex 桌面端与 CLI。当前官方 插件文档 将 IDE 扩展的插件支持排除在外；IDE 如需试用，单独验证直接配置 Skill 与 MCP 的方式。

首版由用户显式选择“项目开发”技能启动。AGENTS.md 增补简短入口指引与稳定约定，保留已有项目指令；详细知识按需求加载。Skills 是流程引导，MCP 是工具接口，接入本身不构成每次修改必经的强制门禁。

3. 系统结构与职责

部分 职责 边界
Codex 查找与阅读实现、理解需求、分析影响、修改代码、执行验证 语义判断由 Codex 或同事完成，并保留依据
项目开发 Skill 组织开发步骤、调用工具、处理待确认项、汇总结果 流程执行率需要实际验证
AGENTS.md 稳定的项目约定、技能入口与知识位置 控制长度，不堆放全部业务材料
本地 MCP 筛选知识、保存清单、采集 Git 变更元数据、检查记录完整性、保存经验草稿 文件被修改不能直接判定业务要求已满足
项目知识 已确认惯例、业务规则、业务关联及参考实现 记录来源、范围与复核状态

推荐 TypeScript/Node 实现本地 STDIO MCP 服务。使用固定版本的运行包，以明确的工作树绝对路径启动服务，不能根据插件安装目录推测项目位置。独立 worktree 初始化时重新绑定对应路径。启动时解析真实路径并检查 Git 仓库身份，所有读写限定在该工作树及约定的本地状态目录；STDIO 的标准输出用于协议，诊断日志输出到标准错误。

模型推理沿用 Codex。首版检索采用模块、路径范围、标签和关键词筛选，不引入独立推理服务或复杂索引。源码搜索、阅读及完整 diff 分析仍使用 Codex 原生能力；MCP 只补充可靠的知识与任务状态管理。

4. 知识与任务数据

建议项目目录如下，名称均为设计示例：

text
repo/
  AGENTS.md
  .agents/skills/project-dev/SKILL.md
  .codex/config.toml                 # 试点 MCP 接入配置
  docs/project-dev/
    project.yaml                    # 模块、路径与知识分类
    knowledge/*.md                  # 经审查共享的规则与经验
  .project-dev/local/                # Git 忽略，按工作树与任务隔离
    tasks/<task-id>.json
    proposals/<proposal-id>.md

知识文件使用 Markdown 正文和 YAML 元数据。每条至少包括 id、type、status、适用模块或路径、适用条件、规则、原因、来源、确认人和复核日期。类型包括代码惯例、业务约束和关联改动经验；状态包括候选、已确认、需复核和已停用。

来源应指向代码位置、设计记录或同事确认过的经验。源码归纳结果先作为候选，避免把偶然实现当作全项目约定。来源文件变化时提示复核；遇到规则之间、规则与现有代码之间的冲突，返回相关依据，由 Codex 或同事判断。首版不承诺自动识别全部语义冲突。

每项改动清单记录：目标组件或位置、需要修改或验证的内容、为何相关、来源、处理状态、核对者和结果证据。状态建议为待处理、已核对、无需处理；“已核对”和“无需处理”均需要理由或证据。

任务记录还包括 schema_version、任务 ID、工作树标识、起始 HEAD、需求与验收条件、采用的知识版本、清单、验证记录、人工纠偏及修订号。使用任务锁、修订号检查和原子文件写入，避免同一任务的更新互相覆盖。共享知识进入 Git；本地任务记录用于恢复与效果统计。

5. 拟议 MCP 工具

下表为产品自定义接口草案，不是 Codex 内置工具。

工具 输入重点 输出与行为
task_open 需求、任务范围 检查仓库起始状态，记录 HEAD，返回任务 ID
knowledge_search 关键词、模块、相关路径、结果上限 返回适用知识、来源、确认状态和复核提示
task_update 任务 ID、修订号、约束与清单、核对记录 校验结构并保存新的任务版本
task_check 任务 ID 获取实际变更路径，返回未核对项、缺少证据项、清单外变更和归属异常
experience_propose 任务 ID、纠正理由、适用范围、来源 保存本地候选经验，返回可审查草稿

MCP 做筛选、结构校验、存储和确定性的清单比对。影响范围的语义分析与业务判断由 Codex 完成，不能把关键词匹配包装成完整的影响分析。

task_check 将“文件是否变化”和“要求是否得到核对”分别报告。例如，文件虽然修改，但相关业务约束仍缺验证证据，清单项应保持待核对。逻辑正确性仍需要相关测试、代码依据和必要的人工判断。

6. 一次开发的执行流程

  1. 同事显式启动技能并描述需求。Codex 整理验收条件，调用 task_open 建立任务。
  2. 检索匹配的项目知识，阅读相关源码与同类实现。Codex 形成方案和改动清单，经 task_update 保存；关键业务不确定点通过对话确认。
  3. Codex 实施修改、执行验证。发现新的关联点或收到纠正时，更新清单，记录修改原因。
  4. 调用 task_check 获取结构性差异和未核对事项，结合完整 diff 与验证结果逐项核对；完成报告注明仍待确认或未完成的事项。
  5. 对有复用价值的纠正调用 experience_propose。同事审查后，由 Codex 形成共享知识文件变更，按团队既有 Git 审查方式确认和发布。

只保存与当前需求有关的经验草稿，不自动采集整个对话。经验积累体现为共享知识的新增与修订，后续任务通过检索使用；不涉及模型权重训练。

7. 起始版本、故障与维护

首版任务采用已有提交的干净、专用工作树，优先使用独立 Git worktree，并记录起始 HEAD。这样可以将从起始版本至当前工作区的差异以及新增未跟踪文件作为本次变更候选。每个工作树只进行一个受跟踪任务，启动与恢复时检查任务锁；任务期间由开发者保证不并发进行其他修改。

task_open 检测已有未提交修改，不自动暂存、重置或归入新任务；先隔离任务再建立基线。脏工作区的精确快照与归属分析留到后续扩展。服务能检测分支变化、起始版本不再可达等明确异常；任务内正常提交仍以起始版本比较，不因 HEAD 正常推进直接判定失效。Git 元数据无法识别所有外部修改来源。对未显露于元数据的并发改动不保证自动识别，发现或获知后需人工核实基线与变更归属。

MCP 不可用时，Skill 明确显示经验检索或清单核对未执行，Codex 可以继续使用现有项目文件；完成结果标记为核对不完整。任务状态有版本号，失败后可恢复。代码引用与知识状态定期复核；停用记录保留历史来源。

本地服务仅在绑定项目内读取必要内容、写入状态和草稿；代码修改由 Codex 的现有权限机制处理。知识不保存凭据或无关对话。索引与任务记录在本地保存；提交给 Codex 的相关上下文仍受既有模型使用方式和团队政策约束，不能据此声称代码完全不离开本机。

8. 关键决策与取舍

决策 理由 取舍
ADR-01：沿用 Codex 对话与执行能力 同事已有使用习惯，集中解决项目依据与变更完整性 首版依赖 Skill 的流程遵循；执行是否完整需要记录
ADR-02：本地 MCP + Git 知识文件 部署轻，知识可审查，任务状态可恢复 团队需同步知识版本并承担少量维护工作
ADR-03：先规则筛选与人工确认 可用已有代码和少量经验起步，便于追溯 召回不全、隐含经验缺失，需要试用补充
ADR-04：先单仓、干净工作树 变更归属明确，减少首版复杂度 暂不覆盖已有大量未提交修改与跨仓任务

9. 实施与验证建议

按一名研发在熟悉的仓库中推进，建议分为约 4–6 周的试点；这是初步估算，需在确定语言、任务类型与投入后调整。

阶段 工作 可检查成果
第 1 周 选择常见需求，整理少量真实案例与关键规则；验证仓库 Skill + 本地 MCP 接入 可运行的接入样例、Skill 基线、知识样例
第 2–3 周 实现知识检索、任务状态、清单核对与经验草稿 在试点任务中跑通完整流程
第 4–5 周 同事试用，补充遗漏规则，调整提醒与检索，打包团队插件 实际使用记录与可分发安装包
第 6 周或试点结束时 对比效果、复盘局限、整理分享 评估结果、改进清单、至少一次内容分享

建议先选约 8–12 个历史或真实需求做回放，再进入日常试用。至少比较“当前 Codex”“Codex + 同一份项目知识与 Skill”“增加 MCP 状态管理后的完整方案”，区分知识整理、流程引导和工具服务各自的收益。回放固定起始版本、需求、模型与关键配置，并由熟悉业务的同事独立核对；小样本用于发现问题，不据此承诺普遍提升比例。

记录人工纠偏的类型与次数、关联漏改及补改、纠偏与返工时间、提醒误报、额外阅读或确认负担，以及流程步骤实际执行率。完成次数、知识条数和安装人数作为使用信息，不能替代开发质量改善。

技术验证重点包括工具可用性、路径隔离、任务更新与恢复、Git 基线识别、规则状态过滤，以及“文件已改但业务未核对”仍保持未完成的情况。产品验证重点是同事是否少纠正、少补漏，新增提醒是否值得处理。

10. 首版完成标准与后续评审点

首版应满足：同事能在 Codex 启动技能；能找到带来源的适用规则；每次任务有可追踪的改动清单；能暴露未核对和疑似遗漏；能生成经人工审查的经验变更；真实任务中有可核查的效果记录，并完成一次实践分享。

通用工具开发从自建 Git 样例开始。进入真实试用前确定试点仓库、常见需求类别、主语言、同事使用的 Codex 客户端和实际投入；这些信息影响项目接入与效果验证，不阻塞通用能力开发。方案在样例接入与真实任务验证后继续修订。
