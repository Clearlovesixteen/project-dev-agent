Codex 项目开发 Agent 实施计划 v0.1

保留各阶段的工作拆分、验证标准与当时的进度记录。

历史记录2026.10.13约 9 分钟阅读

历史设计记录。 以下保留制定时的内容和进度；当前安装与使用方式请以安装指南为准。

日期：2026-10-13。状态：v0.1 通用工具已实现，安装包在新目录验证通过；Codex CLI 协议冒烟与完整合成需求回放通过。桌面插件安装和真实业务对照仍待执行。

目标： 开发可接入不同 Git 项目的通用 Codex 工具包，帮助同事遵循项目惯例、理解业务约束、完成关联改动，并复用经确认的经验。

架构： Codex 负责源码理解、实现与验证；项目开发 Skill 组织流程；TypeScript 本地 STDIO MCP 服务负责知识筛选、任务状态与结构核对。项目差异通过配置和知识文件表达。

技术栈： TypeScript/Node、MCP TypeScript SDK、Markdown/YAML 知识文件、本地 JSON 任务状态、Git。依赖版本在初始化时核实并通过锁文件固定。

执行方式： 在当前任务中逐项推进，每个里程碑保留可审查成果。落实实现时使用既有执行计划、编码与技能创作流程；不依赖缺失的 superpowers 命名空间。本文原计划中的文件职责已按实际模块收拢；源码在 project-dev-agent/，实际入口与验证状态以 README 和 docs/verification.md 为准。

对应设计：初步技术方案 v0.1。本计划进一步明确：真实试点项目用于后续效果验证，不是开始通用工具开发的前提。 第一阶段使用自建的小型 Git 样例。

1. 总体顺序与验收点

顺序 任务 交付物 完成条件
T1 初始化工具仓库、数据契约与样例 构建脚本、数据类型、可创建的 Git 样例 可以构建并运行一个已知关联改动场景
T2 跑通 Codex Skill + MCP 最小流程 task_open/update/check 与技能初稿 在 Codex 完成一次任务并暴露故意遗漏的清单项
T3 补齐状态、版本基线与恢复 证据校验、锁、版本冲突和恢复行为 中断、冲突、基线异常均不产生虚假的完成结果
T4 增加项目知识检索 知识模板、knowledge_search 能返回适用知识及来源，并用于任务清单
T5 增加纠正经验复用 experience_propose 与审查流程 上一次确认的经验能用于下一次类似任务
T6 完成安装与插件分发 安装指引、项目初始化、插件包 在新的目录和干净环境跑通安装与一个任务
T7 真实项目试用、对比与分享 原始任务记录、评估报告、分享材料 能判断是否减少纠偏、补漏，以及增加了多少负担

依赖顺序：T1 → T2 → T3 → T4 → T5 → T6 → T7。T1 后可以并行准备样例知识；评价记录格式可以与 T2 并行制定。正式评估在流程稳定、条件冻结之后开展。

首个里程碑为 T2：同事在 Codex 发出需求，工具保存关联改动清单，修改后指出尚未核对的位置。 T3 是进入多人试用前的必要条件。

关键契约：

text
Task
  id, schema_version, revision, repo_identity, worktree_path
  baseline_head, baseline_branch, phase
  requirement, acceptance_criteria, knowledge_versions
  change_items[], validations[], corrections[]

ChangeItem
  id, target_path_or_component, action(modify|verify)
  requirement, rationale, sources[]
  status(pending|checked|skipped), reviewed_by, evidence[]

Knowledge
  id, type, status(candidate|confirmed|needs_review|disabled)
  modules[], paths[], applicable_conditions
  rule, rationale, sources[], confirmed_by, reviewed_at

ToolResult
  outcome(ok|incomplete|error), code, data, diagnostics[]

工具执行成功和开发任务核对完成是两个不同状态。checked 必须附核对者及证据；skipped 必须附无需处理的理由；源码文件变化不能自动把清单改为 checked。

验收：样例仓库可重复创建；三类问题均有可以识别和核对的案例；领域类型不包含固定业务项目的路径或专有规则。

  • 实现 task_update：保存需求约束、清单与核对记录，校验状态和必要证据。

验收场景：先将全部预期位置记录为待处理，只修改写入逻辑。task_check 应保留登录校验等未核对项，并明确显示“写入文件发生变化，但清单尚未核对”。补齐代码与验证记录后，才逐项记录核对结论。

该场景验证清单追踪能力；它不代表 Agent 已能自主发现所有关联位置。自主影响分析的效果在后续独立案例中验证。

4. T3：状态可靠性、基线与恢复

计划文件：

text
src/storage/lock.ts
src/storage/atomic-write.ts
src/domain/transitions.ts
src/git/baseline.ts
src/tools/task-update.ts
src/tools/task-check.ts
tests/task-recovery.test.ts
tests/task-concurrency.test.ts
tests/git-baseline.test.ts
tests/path-boundary.test.ts
  • 增加工作树活动任务锁和任务写入锁，定义进程退出后恢复与陈旧锁处理方式。
  • 修订号采用比较后更新；旧修订号返回冲突，不覆盖新状态。
  • 文件原子写入；中断后保留上一个完整任务版本。
  • 定义任务阶段 active/closed/aborted；通过 task_update 结束或中止任务，释放活动任务锁。
  • closed 要求所有清单项有有效处理记录，验收项有相应记录；aborted 保留未完成状态和原因。结构满足不宣称逻辑绝对正确。
  • 校验仓库身份、分支、起始版本可达性；分支切换或起始版本不再可达时返回 incomplete。任务内正常提交继续与起始版本比较，不因 HEAD 正常推进判定失效。
  • 处理 staged、unstaged、重命名、删除和新增未跟踪文件；本地状态目录被 Git 忽略且不计入业务修改。
  • 检查路径越界、符号链接与异常 task ID；限制知识读取、任务和草稿写入范围。
  • 运行类型检查与上述行为测试；重启服务验证同一任务可恢复。

重要边界：同一工作树只运行一个受跟踪任务，任务期间避免外部并发改代码。任务锁管理工具自身状态，不能识别所有编辑者和外部修改。Git 命令采用参数调用和结构化解析，避免从用户文本拼接 Shell。

验收：旧版本写入冲突、MCP 断开、任务中止、分支切换、源码文件已改但证据缺失等情况，都不能表现为已完成；结束任务后可建立下一次任务。

9. 实施节奏与当前状态

建议先以一个迭代完成 T1–T3，使流程能运行且可恢复；随后推进 T4–T6，使经验可复用且同事可安装；最后开展 T7。沿用技术方案的 4–6 周作为粗估，实际日期取决于投入和样例接入结果。

可以并行准备：规则样例、历史纠正案例、评价口径。核心任务状态契约与 Skill 调用流程先统一，避免多人同时修改接口和同一工作树。

当前交付：五个 MCP 工具、通用 Skill、Git 任务存储与基线、知识检索与来源复核、候选经验和显式审查、项目初始化、合成样例及试用/分享模板。Codex CLI 已跑通知识检索、任务核对与中止，另一次完整回放完成样例修改、7 项测试和任务关闭。
