本机自动诊断上报修复

目标：在当前电脑完成已安装插件收尾自动发送、接收端持久确认、D1 查询交叉验证。先验证本机，再处理同事首次接入配置；本次不更改团队默认上报策略。

已复现的原因

Node 进程没有使用 macOS 已配置的 HTTP 代理，直接访问 workers.dev 超时。经既有代理请求可达，后端已确认实际批次并写入 20 条元数据。原发送超时 1.5 秒，与独立钩子的软期限相同，容易在网络或冷启动抖动时先终止确认流程。

实现选择

方案取舍
诊断专用传输模块，使用兼容 Node 18 的 Undici采用。仅诊断请求使用代理，不改变进程全局网络；读取既有环境代理，macOS 补读系统 HTTP/HTTPS 代理，回环地址直接连接。
统一升级 Node 并设置全局环境代理需要改变同事环境和其他请求，不用于本次修复。
外部 curl 子进程负责发送增加运行时工具依赖和凭证输入管理，不用于插件正式实现。

执行步骤

  1. 在 tests/diagnostic-transport.test.ts 与独立钩子集成测试中复现：环境代理、系统代理、NO_PROXY、断连、延迟确认与队列去重。
  2. 新增 src/observability/transport.ts，负责代理选择和有界单次请求；uploader.ts 保留批次、游标和退避职责，不记录代理凭证或原始异常。
  3. 仅延长异步 Stop 的预算：网络最多 4 秒，钩子内部最多 6 秒、宿主最多 8 秒。会话开始和用户输入保持原有短期限；未结束输入仍有界退出。停止采集与关闭上传继续有效。
  4. 运行代理和真实打包入口测试、Node 18.19.0 运行检查和完整回归。Node 最低版本、现有接收端、工作目录及项目资料不变化。
  5. 用实际机器的系统代理和构建后的 Stop 入口发送，核对 ACK、游标推进与 D1 条目；通过后按原生更新流程安装修复版，核对钩子加载与信任。需要重新信任时由用户完成，禁止改写信任文件。

验收边界

HTTP 返回成功、D1 实际入库、后续重试无重复行三项互相验证。受控钩子调用与真实宿主事件分别记录，不把手工触发测试当成用户开发成效。诊断错误不影响正常开发；日志、报告与公共仓库均不包含写入密钥、源码或对话正文。
