开发者诊断怎样使用

目的：帮助插件维护者按真实执行结果定位问题、修复和复测。普通使用者继续开发，不增加打分、导出周报或管理流程。

本次提供本地诊断、Workers + D1 收集端和维护者报告。在线服务由维护者在自己的 Cloudflare 账户部署，公开插件不内置团队地址或凭证，远程默认关闭。控制面发布成功后，还需从实际使用环境验证接收链路；钩子与 MCP 的执行失败均独立降级。

数据怎样流转

本插件钩子 / MCP / 验证器→严格白名单 · HMAC 去标识→本地 JSONL→已说明并启用后 · 限量发送→Worker /events · 只写令牌→维护者 D1 私有数据库

每批最多 50 条，单事件最多 4096 字节。只有接收端确认持久提交后才推进游标；确认丢失可安全重试，同一安装和事件 ID 去重。关闭 / 重开 / 更换接收端生成新周期，旧周期不补传。HTTPS 之外只允许本机回环 HTTP 用于测试。响应大小、发送时间、重试频率均有上限。

为什么不直接存 GitHub

GitHub Pages 是静态托管，不能充当接收 API。通过仓库写入或 dispatch 需要写权限凭证，不应把你的 GitHub Token 放进同事插件。当前方案由 GitHub 管理服务代码，Workers 运行接收 API，D1 保存元数据；公开代码中没有诊断数据或读取凭证。

维护者部署步骤

  1. 在维护者自己的 Cloudflare 账户创建 D1 数据库，保存数据库 ID。无需私人服务器或自购域名，但需要该服务账户及自己的资源额度。
  2. 在仓库根安装维护依赖后构建：node tools/diagnostics-collector/build.mjs。同事不需要安装 Wrangler。
  3. 复制 wrangler.example.toml 为该目录下的 wrangler.toml，填入自己的数据库 ID；该本地配置已被 Git 忽略。
  4. 使用已登录的维护者 Wrangler 初始化数据库并部署。本次实测授权范围为 account:read、user:read、workers:write、workers_scripts:write 和 d1:write；独立的 Workers Scripts Write 负责脚本、子域名与触发器管理，不能只选 Workers Write。首次发布前，先在 Cloudflare 的 Workers & Pages 页面初始化账户的 workers.dev 子域名。令牌通过交互式 secret 输入，不放进命令参数、聊天、提交或日志。
npx wrangler@4.155.0 login --device --scopes account:read user:read workers:write workers_scripts:write d1:write
cd tools/diagnostics-collector
npx wrangler@4.155.0 d1 execute project-dev-diagnostics --remote --file schema.sql
npx wrangler@4.155.0 secret put WRITE_TOKEN
npx wrangler@4.155.0 deploy

本次维护端实测 Wrangler 4.155.0，运行它需要 Node 22 或以上；同事仍沿用插件原有的 Node 18.19.0 最低要求，不需要安装 Wrangler。按工具提示完成登录，并在 Cloudflare 页面核对授权。WRITE_TOKEN 至少 16 位随机字母、数字、下划线或短横线；它只用于该接收 API，不授予 GitHub 或数据库读取权限。收集端仅提供 POST /events，其他路径均返回 404。生产服务应保持账户访问控制和资源额度监控。

用 GitHub 更新收集端

可在 Workers 的 Builds 中连接本 GitHub 仓库。仓库根作为构建目录，构建环境设置 PROJECT_DEV_DIAGNOSTICS_DB_ID 为自己的数据库 ID，选填 PROJECT_DEV_DIAGNOSTICS_WORKER（需与平台 Worker 名称一致）。构建命令为 npm ci --ignore-scripts && node tools/diagnostics-collector/build.mjs && node tools/diagnostics-collector/configure.mjs；部署命令为 npx --yes wrangler@4.155.0 deploy --config tools/diagnostics-collector/wrangler.toml。生成配置不会提交 GitHub，WRITE_TOKEN 放 Worker 运行 Secret。数据库初始化只需由维护者先执行一次。若采用其他部署系统，保留相同的构建、初始化与密钥隔离原则。本地 Wrangler 发布不会自动建立 GitHub 联动；需要维护者另行连接自己的仓库。

给同事启用

  1. 先用本机回环测试，再从实际使用机器验证在线服务：未授权请求应拒绝，成功批次收到相同 batch_id 和条数，重复请求不重复入库，实际上传器能在默认 1.5 秒超时内获得确认。默认域名若在使用环境中解析或连接失败，先更换为可达地址再启用；不能把控制面发布成功等同于上报链路已打通。
  2. 向同事一次说明接收方、采集范围和关闭方式。插件设置中配置实际的 https://你的服务/events、写入凭证、notice_version: 2026-10-29-v1 和 upload:true。不在公开仓库预填团队凭证。
  3. 之后在原生 Stop 钩子后台限量发送。没有钩子信任、网络或有效配置时不会声称已上报；正常开发继续。关闭后不再发起新发送，已开始的一批可能在有界超时内完成。

维护者怎样分析

node /实际插件/runtime/cli.mjs insights issues --days 7
node /实际插件/runtime/cli.mjs insights trace --id 实际链路摘要 --days 7
node /实际插件/runtime/cli.mjs insights report --days 7 --output /已有目录/新报告.html

本地命令读取当前机器诊断。跨成员统计在维护者自己的 D1 账户下查询，不向普通用户开放读接口；可以在维护者账户通过 Wrangler 执行 SELECT payload FROM events ORDER BY occurred_at DESC LIMIT 1000，使用 --json 保存到私有本地文件，再用 insights report --file /私有目录/d1.json --days 7 --output /私有目录/团队诊断.html 生成同口径报告。导入文件上限 1 MB，超限分批；查询 LIMIT 造成的覆盖范围由维护者明确说明，不将导出样本当成全量。修复前后按版本、事件、错误码及同一口径比较，样本不足时明确说明，不推算返工工时或遗漏改善率。

诊断边界

  • 可确认：钩子是否进入、辅助查询是否成功、资料是否输出、回执是否匹配、任务是否绑定、工具是否返回错误、验证器是否真实结束，以及出现问题的版本和链路。
  • 不能直接确认：Codex 是否理解业务、是否真正采用上下文、所有复用和关联修改是否正确。基础事件不含正文，语义问题仍需结合用户明确反馈和实际代码核对。
  • 只统计本插件观察到的事件。钩子未加载、宿主未信任、SDK 在 handler 前拒绝参数、进程被硬杀和绕过插件的操作可能形成缺口。回执不等于使用效果，待复核及保护性拒绝也不必然是插件缺陷。
  • 本地保留 30 天、每日约 1 MiB；接收端按接收时间保留 30 天。安装 ID 是随机标识，项目 / 会话 / 任务是本机 HMAC，仍作为诊断标识保护；不称作不可关联的完全匿名数据。
  • 不采集代码、需求、聊天、查询正文、命令、原始异常或真实路径。关闭本地采集会同步停止远程；历史业务资料不因关闭诊断被删除。
