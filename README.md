# Project Dev Agent

**让 Codex 在改代码前了解项目惯例、业务背景和相关改动范围，并把开发中的纠正经验留给下一次任务。**

这是接入 Codex 的开发辅助插件，通过**项目结构扫描、业务建模、历史习惯整理和关联改动检查**，帮助 Codex 按当前项目的实际情况开发。适合已经用 Codex 修改项目、但仍需要反复纠正实现思路的开发者，可以用于不同业务项目。

当前版本：**v0.13.5，供个人使用和小范围团队验证**。通过公开的 GitHub 插件源分发原生 Codex 插件，运行代码和依赖已打包。同事无需克隆源码、运行 npm 或手动同步 Skill。

**诊断默认开启，可关闭。** 新安装首次运行插件 MCP 或已信任钩子时，会自动向本插件维护者 Clearlovesixteen 的 Cloudflare 接收端发送运行元数据，用于修复插件。**不发送源码、PRD/SDD、对话正文、命令或真实路径。** 无需配置服务器或凭证，也没有前端页面。关闭方法：`$project-dev-setup 关闭远程诊断上报`。已保存的关闭状态和自定义接收配置不会因更新被覆盖。

## 它能帮你做什么

| 能力 | 解决的问题 | 具体做法 |
| --- | --- | --- |
| **项目结构扫描** | 不熟悉项目组织方式与已有实现 | 建立文件、模块和静态引用索引，辅助 Codex 查找同类页面、公共组件和已有封装。 |
| **业务建模** | 每次都要重新解释业务背景 | 按业务能力整理术语、状态流程、逐条规则与异常；规则绑定依据，业务关系辅助发现关联入口，默认读摘要，按需读详情与局部修订。 |
| **历史习惯整理** | 已经纠正过的问题重复出现 | 分批分析本机项目对话，提取带用户原话的习惯候选；支持暂停续跑、纠正误提取和停用候选，保留旧版依据。 |
| **关联改动检查** | 只改当前文件，遗漏其他入口 | Codex 结合代码引用与业务关系建立“修改 / 验证”清单，工具对照 Git 变更检查覆盖与待处理项。 |
| **业务验证与效果统计** | 只验证正常路径，或无法判断实际收益 | 从规则整理正常、边界和异常验证建议，绑定现有验收；从本地任务统计纠正与验证现状，有真实同口径配对才比较。 |
| **任务与经验保留** | 换个对话就丢失进度或纠正原因 | 保存需求、验收、验证记录和纠正经验；证据绑定代码指纹，代码再次变化后需要重新核验。 |
| **默认生码规则** | 职责混杂、重复造组件、注释和用户要求遗漏 | 编码前明确模块与选型，编码中维护要求和注释，结束后按实际代码核对五项约束。 |
| **PRD / SDD 落地** | 设计文档与当前项目实现之间仍有空缺 | 沿用已有规格，核对源码、公共能力和业务规则，将设计条目接到实际改动与原有验收。 |
| **自动参与与修改前检查** | 忘记命令、自然表达漏触发或修改前未读取项目依据 | 新安装默认 auto；旧 manual 在新版首次运行时自动迁移为 auto。信任钩子后提供入口，在支持的修改工具执行前核对上下文、任务、实现依据和修改范围。 |
| **开发者诊断** | 维护者缺少插件实际失败与耗时的依据 | 记录严格白名单运行事件，默认策略可远程上报且可关闭，按版本和链路定位问题，不要求用户填写报告。 |

例如，修改一个订单状态的展示时，Agent 会先查找已有状态定义和展示组件，再核对列表、详情、筛选项及测试是否涉及这次变化。需要同步修改的地方和只需验证的地方都会进入清单；实际范围仍需结合当前代码判断。

## 配合 SDD：让方案落实到当前项目

**SDD 说明这次要怎样实现，插件补充在当前仓库中实现所需的项目依据。** 已有 SDD 直接沿用，不要求重新生成一份技术方案；Codex 仍负责理解文档、阅读代码、生成实现和运行检查。

```text
提供 SDD（也支持 PRD、PRD + SDD）
  → 核对需求来源、待确认设计与验收
  → 查找当前项目的实现入口、复用能力和业务规则
  → 将 SDD 条目对应到实际改动位置、实现选择和验收项
  → Codex 编码，维护关联改动与新增纠正
  → 执行真实检查、核对业务场景，更新模型与任务记录
```

| SDD 已经提供什么 | 插件辅助 Codex 补什么 | 如何用于生码 |
| --- | --- | --- |
| 业务行为、状态和限制 | 比较代码当前行为与需求预期，读取规则的条件、例外和来源 | 明确哪些业务规则要变、哪些必须保留，不把局部放开误写成全量放开 |
| 页面、接口、字段和实施步骤 | 定位真实文件、类型、统一请求入口、公共组件及同类用法 | 沿项目分层复用已有实现；接口和字段仍需核对真实契约 |
| 计划修改的模块 | 结合静态引用和已记录业务关系，补充需要修改或验证的其他入口 | 建立关联清单，避免只实现 SDD 中点名的单个页面 |
| 测试与自测说明 | 将原有验收对应到需求来源、正常/边界/异常场景及项目检查计划 | 核对实际结果；来源或代码变化后，相关验收重新核验 |

例如，一份示意 SDD 要求“已关闭订单允许修改备注，商品和金额仍不可改，列表和详情都能进入”。Agent 应先查现有请求服务、弹窗及表单用法，再核对关闭状态的规则和各入口，把备注可改、受限字段不变、两处入口及提交行为对应到验收。是否需要新建组件、调整旧接口，取决于实际源码和契约，不能由示例推定。

同一需求的[使用前后对比图](docs/assets/order-remark-plugin-comparison.png)展示实现复用、业务边界和关联验收三组示意；[团队演讲稿](docs/team-introduction.html#comparison)内可放大查看或下载。图示用于解释可能的偏差与目标行为，不是真实运行截图或效果实测。

用户只需提供当前会话可读取的文档并说“`$project-dev 根据这份 SDD 开发`”；新安装默认 auto，宿主信任钩子后也可直接提交开发请求。文档解析由 Codex 完成，插件不提供独立文档解析或第二套生码服务。只有 PRD 时，先核实影响实施的接口、边界等缺失事实，再继续；SDD 标注“由 PRD 推导、待人工复核”的内容也不会自动成为已确认契约。

## 新模块也要先遵循项目规范

**独立的是业务职责，公共基础设施继续复用。** 编码前先取得项目实现上下文，实际阅读适用规范、相似模块、公共入口及用法，再确定职责划分、设计方式和复用选择。新目录尚不存在时仍返回项目级线索；不能因局部查询没有命中，就认定项目没有既有封装。

从 **0.9.0** 起，这是一条所有开发任务共用的流程：

1. **先找依据**：定位适用规范、相似模块、共享实现与已有用法，新建目录也会提供项目级候选。Codex 实际阅读内容，再结合需求及已核实历史判断适用范围。
2. **作出实现选择**：用少量具体决策说明模块怎样分工、哪些已有方式应沿用、是否需要扩展或偏离以及原因。代码风格、注释、组件选型和用户要求按任务相关性纳入。
3. **接到原有验收**：Agent 自动记录真实原文引用与决策，每项关联现有验收项。MCP 核验路径、哈希、行文及关联关系，新任务缺失依据不能关闭。
4. **对照代码复核**：方案变化追加历史，相关验收先重新打开，保存后再检查；不能靠回传旧结论刷新证据。晚补依据会标明已有代码改动，不记成编码前准备。

请求库是复用问题的一个例子，职责划分、依赖边界、扩展方式与其他约定同样走该流程。原有 HTTP 静态检查继续保留，作为额外保护，不代表覆盖了所有设计问题。新安装默认 auto，已信任钩子为每轮提供轻量入口，不再依赖开发关键词命中。实际修改前核对本轮任务、上下文查询、实现依据和目标位置；用户仍可沿用明确调用。

**边界：** MCP 校验可核对的依据、记录与当前验收；已信任的原生 `PreToolUse` 对支持的补丁和终端路径补充修改前检查。终端任意脚本无法完整推导目标，一些特殊工具也可能不经过钩子；宿主未运行钩子或强制超时可能放行，不能视为全局写入沙箱。真实引用不证明模型已理解代码或设计合理。未适用的旧习惯不强行沿用；语义与质量仍由 Codex 审查并结合项目验证。旧任务兼容保留，明确标为 `legacy`，不补造历史。

## 使用方式：自动参与与明确调用

**新安装及旧版升级均自动进入 `auto`。** 在 Codex 按宿主要求信任本插件钩子后，直接提交需求、PRD 或 SDD。首次开发自动走 `project_prepare(apply:true)`，只绑定当前 Git 根目录，不需要独立接入命令；已有工作范围保持不变。普通讨论、问答及查看代码不创建开发任务。

安装成功不等于钩子已信任或本轮已参与。初次及钩子定义变化后，宿主可能要求重新审查；插件不代写信任记录。需要宿主支持并实际加载 `SessionStart`、`UserPromptSubmit`、`PreToolUse`、`PostToolUse`、`Stop` 五类钩子；仅看到 Skill 或 MCP 名称不能证明修改前检查生效。

**旧配置自动迁移：** 从 0.13.3 或更早版本升级到 0.13.4 及后续版本后，首次运行插件 MCP 或已信任钩子时，将旧 `manual` 自动切换为 `auto`，包含旧版明确保存的 manual；无需额外命令或手动改配置。已有 auto / observe 保持模式。迁移记录策略版本并只执行一次，之后用户主动切回 manual 的选择会保留。工作目录、项目记录、诊断开关、自定义接收端及上传周期不变。文件损坏、不可写或存在活跃配置锁时保留原文件、显示未完成并在后续启动重试，不假报已生效。

| 模式 | 行为 |
| --- | --- |
| `auto` | 提供项目入口；修改前核对当前上下文、会话任务、实现依据和影响范围；修改后记录待检查情况。 |
| `manual` | 保留明确调用 `$project-dev`，不自动注入、补身份或检查原生修改。 |
| `observe` | 观察有限钩子元数据，不自动注入或阻断修改。 |

日常链路：**提供 PRD/SDD 或自然需求 → 准备项目 → 查询模型和已有实现 → 绑定任务与修改范围 → Codex 修改 → 真实验证和关联验收。** 已有 SDD 直接核对，缺少且影响实施的事实再澄清，不另建规格系统。

- **只读终端分流。** `rg -n "loadData|invoke" src` 的引号内 `|` 是参数。支持已知静态读取命令、全部片段只读的管道/组合、常见 shell 包装，以及 Windows 的 `rg.exe`、`Get-Content`、`Select-String` 等。读取不受其他聊天的活跃任务阻挡，不创建、挂起或接管开发任务。重定向、写文件片段和未知解释器脚本仍需准备；动态变量、命令替换或复杂脚本块不能据外层命令名取得读取豁免。
- **修改前检查。** 已信任 `PreToolUse` 检查支持的 `apply_patch` 与终端工具。缺少准备时返回明确拒绝及恢复步骤，由 Agent 补 `project_context`、`task_open/task_check`、实现依据或关联清单，再重试。标准补丁逐个核对目标文件；未知终端命令先要求准备，但不声称能解析任意脚本的全部写入位置。只读命令、插件管理、分支准备和其他插件工具不强制进入无关开发任务。
- **与专业技能协作。** 专业 Skill 主导实施，本插件补项目依据和质量记录。只为本插件 MCP 补宿主会话/轮次身份，保留 project、需求、修订号和原权限，不改其他 MCP 参数，不覆盖项目 AGENTS。
- **运行异常可见。** 内部修改检查超时或异常返回合法拒绝；范围外明确说明未参与，不自动扩大范围。宿主未加载、未信任、强制终止或特殊工具绕过仍是覆盖缺口，须通过实际调用验收。钩子不运行模型或项目脚本，也不全仓库扫描；同步内部硬期限 1.8 秒，异步 Stop 内部 6 秒、宿主 8 秒。
- **任务接续。** 按项目、工作树、分支和会话恢复任务；同分支仅一个活跃任务，跨聊天不自动接管。切换分支保留原任务；独立需求可由所属会话显式挂起，再建新任务。恢复核对原基线与冲突，不能改写基线或自动中止旧任务。
- **本轮参与状态。** `project_prepare` 返回运行策略与 `participation`：未观测、已查询、已绑定、待检查、检查未完成或已关闭。`current_turn_observed` 区分本轮实际工具记录与历史参与；计数按会话和分支累积。钩子输出、旧任务数量及回执匹配都不能代替本轮执行证明。
- **诊断服务维护者。** 分开统计旧 manual 自动升级成功、升级未完成、主动手动、observe、范围未就绪、修改前准备缺失、修改工具返回及检查缺口。补齐任务阶段和会话关联；复杂终端只记录固定的 `COMMAND_*` 分类/原因码，可区分引号、读取链、Windows、动态语法和未识别能力，不记录原始命令或参数。只统计实际记录的事件，不代表所有终端命令总量。旧事件缺字段保持 unknown，不补猜历史。没有未执行钩子的完整轮次总量，不计算虚假的自动参与率。

自动注入只证明资料已提供，工具记录只证明经过对应调用，**都不能据此声称模型已理解、已复用或代码质量改善**。需要结合代码、真实检查和验收确认。

### 数据记录的设计：开发资料与插件诊断各有用途

记录的目的有两个：**让下次开发能继续利用本项目的事实；让维护者能根据实际运行定位插件问题。** 日常记录由 Agent 和工具维护，不要求同事填表、打分或提交周报。

| 数据 | 保存位置与内容 | 目的 |
| --- | --- | --- |
| 项目开发资料 | 当前仓库 `.project-dev/local/`：结构索引、带来源的业务模型、习惯与纠正、需求与验收、实现选择、实际检查和修订 | 恢复任务、复用经验、发现过期依据，服务当前及后续需求；各项目分别维护，不作为远程诊断正文发送 |
| 插件运行诊断 | Codex 用户目录 `project-dev-agent/telemetry/`：版本、事件、结果码、耗时、输入类型、有限计数与去标识链路；新安装默认限量发送至维护者 Workers + D1，可关闭 | 排查触发、查询、工具调用、验证记录和上报链路的问题；按版本定位和复测修复效果 |

诊断按“**观测事件 → 字段白名单与 HMAC 去标识 → 本地 JSONL → Stop 异步发送 → Worker 校验并持久写入 D1 → 确认后推进游标**”运行。接收端去重，发送有批量、时间和重试上限；失败保留本地队列并退避，诊断异常不应阻断业务开发。代码来源、需求原文和终端命令可以留在本地项目验收记录中，但不能进入远程诊断白名单。

维护者先按“版本 / 事件 / 结果码”聚类，再用去标识链路关联事件和同一任务的相关链路，查看辅助处理耗时、查询结果及可观测缺口。数据从维护者自己的 D1 查询导出，可用现有 `insights` 命令生成私用报告；没有面向安装者的在线管理页面。修复后以相同事件和样本口径复测，不能把日志数量增加、回执匹配或测试通过直接当成生码质量提升。

非 Git 会话正常跳过，范围外项目明确提示插件未参与并保留原范围，分别记录 `NOT_GIT_WORKTREE` / `PROJECT_OUTSIDE_WORKSPACE`；真正失败按目录、配置、任务、查询和回执环节记录安全原因码。历史 `CONTEXT_UNAVAILABLE` 是合并降级码，不能只凭它判断上下文查询出错；`VALIDATION_RUN_REQUIRED` 也可能是关闭保护正确生效，需要结合事件复核。钩子未加载、未获信任或绕过插件的操作可能没有事件，**没有观测记录不等于执行成功**。

### 诊断数据与关闭方式

本地诊断默认启用，保存在 Codex 用户目录的 `project-dev-agent/telemetry/`：每天最多约 1 MiB，保留 30 天。事件白名单不包含源码、PRD/SDD、对话正文、原始查询、命令、原始错误消息和真实路径。项目、任务及会话 ID 使用本机随机密钥做 HMAC 去标识；安装 ID 为随机值，仍按诊断标识保护。

**新安装远程上报默认开启，可关闭。** 发布者默认策略已在安装说明中告知：插件 MCP 或已信任原生钩子首次启动时，若尚无 `runtime.json`，自动配置维护者接收端；不扫描用户正文，不要求日常填写表单。原生 Stop 在后台限量发送：每批最多 50 条，一次最多 4 批，共享 4 秒发送预算，保留内部 6 秒、宿主 8 秒上限。每批收到持久确认立即保存游标，后批超时不撤回前批进度，剩余积压等待后续收尾。首次安装及钩子变更仍需按 Codex 要求审查信任，这与填写上报参数是两件事。

已有诊断配置保持原样，包括旧版本保存的关闭状态、自定义接收端和维护者私有配置。旧 manual 的自动升级仅改变自动参与策略。升级不会擅自开启已关闭的上传。关闭后不再启动新发送，已开始的一批可能在有界超时内结束；重开或更换接收端不补传旧周期。失败保留游标并退避，接收端按事件 ID 去重。GitHub Token、Cloudflare 管理凭证和数据库读取凭证均不分发到插件。

默认接收地址为 `https://project-dev-diagnostics.clearlovesixteen-project-dev.workers.dev/public/events`，由维护者 Clearlovesixteen 控制。它使用可公开的接收标识，只能提交严格白名单元数据；原私有 `/events` 使用独立密钥。来源散列、安装标识和总量限流在 Cloudflare 位置近似生效，不等同严格费用上限。来源 IP 仅用于短暂限流，不写入事件或 D1。公开标识不能认证安装者身份，诊断属于客户端提交的排查线索。

上报只需后端接收接口和数据库，无需前端或自购域名。诊断发送优先使用已有 `HTTPS_PROXY` / `HTTP_PROXY`（小写优先），支持 `NO_PROXY`；无环境代理时，macOS 读取已有静态 HTTP/HTTPS 系统代理。回环地址直接连接，PAC 和仅 SOCKS 的系统代理暂不解析。该配置仅作用于诊断请求，不修改系统网络、全局 Node 网络或业务项目。

```text
$project-dev-setup 关闭远程诊断上报。
$project-dev-setup 关闭本地诊断记录。
$project-dev-setup 切回 manual 模式。
```

设置保存在独立 `project-dev-agent/runtime.json`，工作范围仍在 `settings.json`，两者独立修订保护。必要参与运行状态在 Codex 用户目录 `project-dev-agent/participation/`，不含需求、代码或命令正文；关闭诊断仍保留修改前检查需要的本地状态，不再新增诊断事件或启动上传。关闭自动参与使用 manual。

维护者命令（从实际插件根运行；源码开发改用 `dist/src/cli.js`）：

```bash
node /实际插件目录/runtime/cli.mjs runtime status
node /实际插件目录/runtime/cli.mjs insights issues --days 7
node /实际插件目录/runtime/cli.mjs insights trace --id 实际链路摘要 --days 7
node /实际插件目录/runtime/cli.mjs insights report --days 7 --output /已有目录/诊断.html
```

报告文件必须是新文件，避免覆盖已有材料。报告区分原始异常事件和排除明确关联派生重复后的主信号；历史派生记录即使写成 `incomplete / OK`，也会展示可确认的主调用原因。聚合统计覆盖读到的全部事件，链路明细最多展示 200 条并显示总数；安装标识可能包含维护自测，不能当作同事人数。问题聚类是排查线索，包含待复核和保护性拒绝，不能自动认定都是插件缺陷。钩子未被宿主加载、SDK 提前拒绝参数、绕过插件的操作以及超过保留/容量的记录属于覆盖限制。

收集端源码在 `tools/diagnostics-collector/`，使用 Workers + D1，无需私人服务器，**代码可由 GitHub 管理并部署，事件数据留在维护者的数据库**。本发布版本内置上述公开接收策略；自行分发时可在 `src/runtime/published-diagnostics.ts` 修改为自己的服务并同步安装说明。数据库的 `ingest_source` 区分 `public` 和 `private`，不向普通安装者开放读接口。部署及维护者查询说明见 [开发者诊断交付说明](docs/diagnostics.html)。

本次 Cloudflare 部署验证使用的授权范围为 `account:read`、`user:read`、`workers:write`、**`workers_scripts:write`** 和 `d1:write`；单独的 `workers:write` 不足以管理脚本发布及 workers.dev 子域名。首次部署需初始化账户子域名，并从实际使用机器验证接收地址、持久确认和上传超时。控制面显示发布成功后，仍须通过这些检查才启用远程上报。Wrangler 仅由维护者使用，不增加同事业务项目的依赖。

## 0.11：连续开发与纠正、验收闭环

使用方式保持 `$project-dev 描述需求`，同一需求的继续和纠正沿用流程；不新增用户表单、管理页面或后台进程。

| 修复 | 使用时的行为 |
| --- | --- |
| **已有工作继续开发** | 接入时保存已有暂存、未暂存、新增及删除内容，任务只追踪后续增量；原有工作与暂存状态保留。 |
| **即时保存纠正** | Agent 保存带本项目用户原话、范围及条件的纠正，不依赖活跃任务。后续查询按范围返回候选；修订、替代与停用保留历史，不自动确认团队规则。 |
| **长会话发现新增历史** | 明确开发需求开始、跨日恢复及收尾时检查来源游标，有变动增量重扫；发现新消息与分析完成分开记录。 |
| **业务影响进入任务** | 每项需求说明是否改变业务规则；改变时绑定新版业务模型、变更草案与场景验收。未知继续待核实，旧模型按涉及范围逐条迁移。 |
| **按需求及原型验收** | 验收关联原始要求、PRD、接口或原型版本。原型不可读时视觉项保持待核验，来源更新先重开验收，验收含义与类别修订保留前后定义。 |
| **正式终端调用通道** | 当前会话没有插件工具时，Agent 使用当前运行文件内的正式通道，复用同一 MCP 参数、配置范围与修订校验，避免临时脚本和写死版本。 |

纠正提取、业务影响判断、验收分类与视觉核对由当前 Codex 执行。工具核验来源和结构化记录，不能证明所有用户表达都被准确理解，也不能根据图片哈希判断页面一致。即时纠正只核对本机可读取的项目用户消息；历史剩余批次不在后台自动运行。正式通道可验证独立运行文件，宿主是否加载工具仍须在当前会话核对。

接入前内容保存在 `.project-dev/local/baselines/`：最多2000个改动路径，每文件8 MiB、总内容64 MiB，超限明确失败。起始内容不推断作者，`before_changes` 只表示相对本次接入内容没有后续改动。旧任务继续按原基线及策略运行，不补造历史；各项目资料继续独立。

## 0.10：围绕真实开发的四项改进

开发入口仍是 `$project-dev 描述需求`，以下资料由 Agent 自动维护。

| 改进 | 如何帮助开发 | 实现与边界 |
| --- | --- | --- |
| **精准查找既有实现** | 新模块先找已有能力及真实用法，减少另起封装。 | 根据符号、命名词、标识符及路径排序，结合应用范围返回源码位置、当前指纹和直接使用方；新目录补充项目级候选。当前是本地词法检索，不是向量语义搜索，未命中需继续查代码。 |
| **业务规则变更预演** | 修改前看清“原规则 → 预期规则”，将正常、边界和异常场景接到验收。 | 草案保存在任务中，不覆盖现有模型。实现后核对源码、场景验收与实际检查，显式回写当前行为；保留回执，支持中断恢复和后续要求修订。是否符合业务仍需核实。 |
| **真实检查结果接入验收** | 避免仅凭一句“测试通过”就完成任务。 | 保存检查计划，由 Codex 原终端运行内部执行器，记录命令、退出码、日志摘要和前后代码指纹。生产代码缺少有效运行结果、失败、超时或过期时不能关闭新任务。 |
| **说明规则为什么适用** | 区分本次适用规则和相似线索，减少把旧习惯套进所有模块。 | 返回路径、模块、关键词的匹配理由及仍需核对的条件；候选、停用、过期及人工确认状态保持独立，命中不等于已经确认。 |

业务规则草案针对已建立的新格式模型；遇到未知业务，先阅读代码并建立有依据的模型。一个草案只改一条规则，保存原规则指纹，拒绝覆盖并发变化；不相关规则和旧证据保留。需求变化时追加后继草案，不改写已保存的历史。

检查命令由 Codex 按项目和需求选择，通过原有终端执行及权限流程运行，**MCP 不代替终端执行项目脚本**。执行器使用参数数组、限制时间及日志容量；不能靠 `task_update` 声明生成成功记录。新任务新增此约束，旧任务按 `legacy` 兼容；仅文档等修改可说明检查不适用。运行结果不证明测试覆盖充分或业务正确，本地记录也不防电脑文件所有者自行改写。

## 默认生码规则

从 v0.6.5 起，使用 `$project-dev` 开发时默认遵循下列规则。当前用户明确要求决定任务范围，具体实现结合项目现有约定；历史习惯和业务模型先核对适用条件。

| 规则 | 执行要求 |
| --- | --- |
| **按职责模块化** | 明确业务逻辑、数据访问、页面交互和通用工具的边界，禁止无关函数堆入同一文件。同一职责的辅助函数可以共置，只整理本次涉及的代码。 |
| **合理使用设计模式** | 根据实际变化点评估策略、状态、适配器等模式，并说明原因；简单逻辑保持简单，避免多余抽象。 |
| **保留用户要求** | 记录本次要求和验收项；新增或纠正要求时同步维护记录，结束时逐条核对。可复用要求保留来源、范围，候选不自动成为团队规则。 |
| **配套注释** | 模块说明职责，公共函数说明用途及必要契约，关键业务和复杂实现说明依据与原因；默认中文，修改逻辑时同步维护注释。 |
| **组件依次复用** | **项目已接入的组件库 → 项目已有可复用组件 → 自行实现**。核实实际 API、扩展能力及项目必要约束，进入下一层时说明上一层的不足。 |

编码前给出简短的职责划分与选择理由；实施时维护代码、注释和要求；结束时检查职责混杂、过度设计、需求遗漏、失效注释和重复实现。依据和审查结果写入现有任务清单、验收项和纠正记录，无需额外填写表单。无组件等不适用场景说明理由即可，小改动不强制生成设计文档。

**这些规则由 Skill 指导 Codex 执行。** MCP 继续提供 16 个工具，校验任务记录、证据和代码快照，新增任务还核验通用实现依据及关联验收，保留原有 HTTP 专项保护；模块边界、设计模式和注释的合理性仍由 Codex 审查，也不代替项目测试。详细示例见 [生码规则](skills/project-dev/references/generation-rules.md)。当前版本保留任务、历史、设置及代码指纹规则；旧业务模型继续可读，按需核对后迁移为支持逐条依据的新模型。

### 组件选型怎样判断

按“**项目已接入的组件库 → 项目已有可复用组件 → 自行实现**”依次检查，不根据组件名称或依赖声明直接下结论。

1. **先读组件库的实际能力。** 核对项目已安装版本、导出、类型和真实用法，评估属性、插槽及扩展能力，同时检查必要的权限、样式、交互等约束。满足就复用，不擅自引入另一套组件库。
2. **再核对项目沉淀组件。** 库组件无法合理满足时，查找项目已有封装，判断直接复用或小幅扩展；若扩展共享组件，检查其他调用方的兼容性。已有封装承载必要权限或交互时，不能为使用底层库而绕开它。
3. **最后决定是否自研。** 前两层都存在具体缺口，才说明已读位置、缺口和自研边界，并按职责实现。单纯没有搜到，不等于项目不存在可复用能力。

选择理由写入本次实现依据并关联验收，收尾对照实际代码复核；不让用户额外填写选型表。请求、状态管理、校验等公共基础设施同样先查现有入口与用法，组件顺序不是仅针对 UI 的复用口号。

### 设计模式怎样判断

先读项目分层与同类实现，再判断当前需求是否存在稳定的变化点，以及抽象收益能否覆盖维护成本。**设计模式服务实际问题，简单需求可以明确选择不用模式。**

| 实际问题 | 可考虑的实现 | 采用前核对 |
| --- | --- | --- |
| 存在多种可替换的校验、计价或处理行为 | 策略模式、函数表或函数组合 | 是否真有多种行为，输入输出是否稳定，现有扩展点能否承担 |
| 状态变化复杂，操作受转换规则约束 | 显式转换表或状态模式 | 状态、合法转换、例外是否有业务依据；简单状态判断无需建立类体系 |
| 外部系统接口和字段存在差异 | 边界适配器 | 差异能否集中到边界；是否已有适配层可以扩展 |
| 单字段、文案或简单条件修改 | 沿用已有函数与分支 | 当前结构能否清楚表达，避免增加无实际用途的工厂、接口和继承层 |

Codex 记录“解决什么问题、为何沿用/扩展/新建、有哪些成本、如何验证”，然后结合代码复核；MCP 校验引用和记录关联，不能通过扫描模式名称自动证明设计正确。模块职责与关键取舍写入适用的中文注释，逻辑变化时同步维护。

## 几个核心概念

| 概念 | 含义 |
| --- | --- |
| **项目结构索引** | 记录文件在哪里、有哪些角色、哪些文件存在直接引用，用来定位需要阅读的代码。 |
| **业务模型** | 记录某个模块的业务含义、处理流程、规则职责及对应实现，帮助理解业务在当前代码中如何运行。 |
| **习惯候选** | 从用户历史表达和纠正中提取的开发偏好，带适用范围，需要结合当前需求和代码核对。 |
| **已确认项目知识** | 经过明确人工审查的项目规则；查询时还会检查来源是否有效。业务模型和习惯候选不会自动变成确认规则。 |
| **本次实现依据** | 本需求实际参考的原文、适用约束与实现选择；关联验收并保留修订历史，由 Agent 自动维护。 |
| **业务变更草案** | 本任务要变更的逐条业务规则，包含原规则、预期规则、需求依据及场景验收；通过核验后回写模型。 |
| **真实运行记录** | 终端执行器生成的检查命令、退出码、日志摘要和代码指纹，用于核对本次验收。 |
| **关联改动清单** | 针对本次需求列出的修改位置、验证位置、原因与证据，用来跟踪影响范围和完成情况。 |

## 第一次接入项目，会发生什么

安装插件后，在业务仓库首次使用 `$project-dev` 时开始接入；仅安装插件不会扫描所有项目。

1. **自动检测和初始化。** 定位当前 Git 仓库；未配置时保存该仓库作为工作范围，已配置时复用。在 Git 本地忽略规则中加入 `.project-dev/local/`，用于保存个人记录，不改变共享项目说明和业务代码。
2. **建立结构索引。** 扫描允许读取的源码和配置，识别目录、模块、页面入口、公共能力及直接导入关系，并报告已扫描、排除和未覆盖的范围。
3. **整理项目历史。** 查找本机 Codex 普通及归档会话中能够归属当前仓库的可见对话文本，分批分析并保存带用户原话的习惯候选。日常开发每轮默认最多分析 3 批，有剩余时保存断点并继续需求；后续对话接着处理。明确要求全量分析时持续处理。没有历史也可以继续使用。
4. **围绕需求建立业务模型。** 阅读实际涉及的模块，保存有用的术语、状态流程、业务规则、适用条件、异常和关联实现。每条规则绑定代码、文档或本项目已保存任务的依据，区分当前行为、预期行为与推断。记录由 Agent 维护，无需填写表单。

首次接入先建立结构基础，业务模型通过实际需求逐步补充。后续新开发对话会刷新结构索引；历史追加消息进入新批次，未变化的原批次继续保留分析、纠正和停用决定，日志归档也不会重置已有分析。原话或上下文被改写时需要重新分析。查询相关业务模型时，会核对其来源是否仍与当前源码一致。

历史分析由当前 Codex 会话执行。暂停后不会后台运行，也不会把剩余批次标为已完成；进度会说明已分析和待处理数量。用户主动暂停后，需要明确提出继续；因本轮预算暂停的，下个开发对话会从断点续跑。

**已有未提交改动也可以直接开始任务。** 插件保存接入时的工作区内容，再跟踪后续增量；同一文件在接入前后都有修改也能区分。不会自动 stash、reset、commit 或更改暂存区。检查结果绑定完整有效工作区，接入前内容也参与指纹核对。未解决合并冲突、超出完整快照容量或连接失败时会明确说明，不能当作已接入。

## 业务建模：可靠、精简、按需维护

**业务建模是核心能力。** Codex 负责阅读需求和代码、分析规则与业务关系；本地 MCP 校验引用、版本与条目关系，保存模型并提示需要复核的内容。明确调用或已启用的自动辅助均复用这一能力，模型查询、记录和维护由 Agent 完成。

### 记录什么

| 内容 | 用途 |
| --- | --- |
| 业务对象与流程 | 按业务能力记录稳定实体 ID、术语、带来源别名、状态含义和流程步骤；不因同名自动合并实体，保留未知问题。 |
| 逐条业务规则 | 每条具有稳定 ID、职责、适用条件、异常条件和来源引用，避免只保存一段模糊总结。 |
| 规则性质 | 区分 **代码当前行为**、**需求预期行为**和**待核实推断**。当前实现与新需求不同，应识别差异并纳入开发及验收。 |
| 可核对的依据 | 源码与项目文档保留路径、行号、原文和哈希；本项目任务要求或纠正保留任务 ID、原文及哈希。 |
| 业务关系 | 记录规则实施位置、使用位置或依赖位置及理由；可引用已有模型复用公共概念，帮助发现没有直接代码导入的关联入口。 |
| 修订与待复核项 | 源码、任务纠正、规则内容或关联模型变化时，提示具体受影响的规则与关系；保留旧修订。 |

例如，新增“冻结”状态时，模型可以帮助分析编辑入口、详情展示、提交操作和接口校验是否受影响，并分别说明依据与未知内容。**这是用途示例；实际结论必须来自当前项目，不能把前端限制推断成后端已经校验。**

### 怎样保持精简

- **按需建模。** 首次先建立结构索引，围绕真实需求逐步积累，不要求先读懂全项目。
- **默认摘要。** 新版模型列表每页最多 5 个，先返回相关规则摘要；可按模型 ID、修订号和规则 ID 读取条件、异常、关系及依据。公共概念通过引用复用。
- **局部修订。** 已有新版模型使用 `patch` 按稳定 ID 更新或删除来源、规则、关系；未提交的条目和证据原样保留。单模型上限 64 KiB，超限按业务能力拆分。
- **减少打断。** Agent 自动维护资料，只有影响当前实现且无法从已有资料核实的关键业务歧义才询问。日常输出保持简短，详情按需查看。

### 怎样保持可靠

`project_scan` 刷新结构索引；`project_context` 查询并核对来源；`project_model_record` 校验并保存。模型内的来源、规则与关系使用稳定 ID，工具拒绝悬空引用、重复 ID、过期修订号和不匹配的原文。

**每条规则独立保存依据指纹。** 即使两条规则引用同一文件，也只刷新本次实际复核的规则。只换来源哈希、改摘要或重新扫描，不会把其他旧规则变成已核对。业务关系跟踪本地规则、实体、目标文件和跨模型依赖。新关系可用 `target_rule_ids` 精确绑定目标规则及依据版本，减少无关规则/摘要修订的扩散；旧关系仍按整个目标模型修订号校验。

`needs_rescan` 表示索引需要刷新，`needs_review` 表示业务内容需要重新阅读核对；查询结果给出待复核规则、关系及路径。复核由 Codex 在当前开发会话执行，随后提交局部修订；没有后台自动重写模型的进程。

模型及修订保存在当前项目的 `.project-dev/local/understanding/`，可选报告为该目录下的 `report.html`。报告是生成时快照，实时状态以工具查询为准。

**v0.6.5 及以前的模型继续可读。** Agent 仅在实际需要时读取旧模型，补齐规则依据、条件和异常，再迁移到新版；旧版本保留，不批量编造来源，也不允许用旧格式覆盖新版模型。无需同事手动迁移文件。

**模型始终是候选。** 引用匹配能证明来源存在，不能证明所有业务判断正确。业务关系按方向保存，并建立双向检索索引；默认展开一层，显式请求最多两层，节点、边和输出均有上限，截断会说明。它不能保证发现全部调用或跨系统影响。记录预期行为也不表示用户已批准团队规则；共享知识仍通过原有明确审查流程确认。具体参数见 [业务建模输入说明](skills/project-dev/references/understanding-inputs.md)。

## 0.8 的六项改进

| 改进 | 开发时如何运行 |
| --- | --- |
| **规则分歧检查** | 比较范围、职责、条件及异常一致的结构化断言，返回相互矛盾或代码与需求不同的依据。Codex 核实后处理，关键未知才询问。没有断言的自然语言矛盾仍需阅读判断。 |
| **真实效果统计** | 收尾时自动读取本项目任务的纠正条目和当前验收、验证现状；没有真实同需求、同验收口径对照时明确显示数据不足，不报改善率。 |
| **关联检查补全** | 修改前结合计划路径，修改后结合实际差异，核对双向引用、共享标识符和显式业务关系中的相关入口。提示是核对线索，不表示所有位置都必须修改。 |
| **业务场景验收** | 根据规则条件和异常整理正常、边界和异常建议，适用场景绑定已有验收；显式绑定后，规则或依据过期会阻止沿用旧验收关闭任务。 |
| **重复识别与复用** | 识别明确重复的规则和同名术语差异，提示公共模型引用。由 Codex 核对含义并局部整理，保留来源和旧修订，不自动删除整份模型。 |
| **增量结构扫描** | 复用安全路径和文件元数据未变化的结构记录，显示实际读取与复用数量；新增、删除与别名关系仍刷新。业务依据查询继续核对真实源码。 |

这些改进仍由“项目开发”处理，无需同事添加命令、管理页面或填写质量表单。新字段为可选，旧模型和旧任务继续可读，旧规则不会仅因升级而失效。模型查询、影响分析和场景建议都有容量限制，会明确返回截断情况。

效果统计记录的是**当前已保存事实**：纠正条目数不等于交互次数，当前失败记录数不等于历史失败总次数，也不能推算返工工时。维护者明确安排对照时，可选标注真实 baseline/assisted 样本；夹具、重复分组、不同验收口径、未完成或截断样本不产生真实改善结论。

## 日常怎么用

在 Codex 中调用 `$project-dev`，后面直接描述需求，不需要每次复制一大段固定提示词。

| 你想做什么 | 可以这样说 |
| --- | --- |
| 实现需求 | `$project-dev 帮我实现这个需求：……` |
| 根据 PRD 开发 | `$project-dev 根据这份 PRD 实现需求，先梳理验收项和关联改动范围。` |
| 梳理业务模型 | `$project-dev 整理订单模块的业务模型，保存术语、流程和规则职责，列出源码依据与待确认问题。` |
| 复用业务模型 | `$project-dev 基于已有业务模型分析这次需求的影响范围，先核对相关源码是否变化。` |
| 继续上次任务 | `$project-dev 继续当前仓库上次未完成的任务。` |
| 查看历史习惯 | `$project-dev 分析当前项目的历史习惯，给我查看报告。` |
| 暂停或继续历史分析 | `$project-dev 先暂停历史分析，继续当前需求。` / `$project-dev 继续分析剩余历史。` |
| 纠正误提取的习惯 | `$project-dev “所有页面用原生表单”理解错了，只适用于旧订单页面，请核对原话后修订。` |
| 停用习惯候选 | `$project-dev 停用这条误提取的习惯，保留修订记录。` |
| 纠正实现方式 | `这里应该复用现有封装，另外两个入口也要同步处理，原因是……` |

PRD 需要以当前 Codex 会话可读取的文本或附件提供。附件解析由 Codex 负责；本工具不提供独立的 Word、PDF 或图片解析服务。

习惯修订会保留旧版本，重新扫描不会覆盖未变化批次的修订结果。一个候选可能来自多个批次，Codex 会核对各批次；停用候选不会自动撤销已人工确认的共享知识，后者需要单独审查。

审查或执行验证前，Codex 通过 `task_check` 获取代码指纹，核验后将同一指纹随证据提交。重新核验已有完成项时，还会通过 `reviewed_ids` 明确本次复核的条目；只检查 A，不会让完整列表中 B 的旧证据一起刷新。代码再次变化时，旧证据标为待复核，并阻止直接关闭任务。该机制不代替实际测试，指纹不包含被 Git 忽略的依赖及外部服务状态。

从 v0.6.3 或更早版本升级后，活跃任务的旧证据需要重新核验一次，防止沿用旧版可能误刷新的记录；已结束的历史任务保留。工具和 Skill 会提示 Codex 如何逐项完成，开发者无需手写这些参数。

一个需求通常按下面的顺序推进：

```text
理解需求与验收标准
  → 查询项目结构、业务模型、历史候选与已确认知识
  → 阅读源码，核对业务关系，按需补充模型和关联改动清单
  → 明确模块职责、设计选择与复用依据，保存业务变更草案及检查计划
  → 修改代码并维护注释，记录新增要求和纠正原因
  → 审查适用生码规则，通过原终端执行检查，逐项完成业务场景验收
  → 按实际源码回写业务规则，核对执行结果，保存任务结果和经验候选
```

习惯和业务理解的候选需要结合当前代码核对。候选不会自动变成团队规则；确认共享知识需要显式审查。

## 更新到最新版本

在 Codex 里说：

```text
$project-dev-update 更新 Project Dev Agent 到最新版。
```

它会调用 Codex 原生插件管理器刷新配置好的插件源，并核对安装版本。也可以直接执行：

```bash
codex -c 'marketplaces.project-dev-team.sparse_paths=[".agents/plugins","plugins/project-dev-agent"]' plugin marketplace upgrade project-dev-team --json
codex -c 'marketplaces.project-dev-team.sparse_paths=[".agents/plugins","plugins/project-dev-agent"]' plugin list --marketplace project-dev-team --json
```

**v0.11.1 修复了旧更新入口重复完整克隆仓库的问题。** 官方源只需目录清单和预构建插件两个目录。首次安装使用 `--sparse`；已有安装通过 `-c` 给本次刷新指定相同目录，保留原有仓库地址、SSH/HTTPS 协议与 ref，不必移除旧源，也不修改个人持久配置。已有额外稀疏目录时应合并保留；自定义源不能直接套用官方目录。

遇到下载超时、连接中断或 `early EOF`，更新入口用同一轻量命令最多重试一次。认证、主机密钥、权限和配置错误立即停止；不会自动切换协议或跳过校验。刷新成功后同时核对源版本与安装版本，失败时保留旧版，不把“命令已执行”当作“更新成功”。稀疏下载降低传输量，仍需要网络可达，不保证任何网络条件都能成功。

已实测：刷新 Git 插件源会更新已启用插件的版本缓存。更新后**新建对话或重启 Codex**，使 MCP 进程和 Skill 加载新版；运行中的旧对话不会自动切换。更新前先完成或保存当前开发任务。

工作目录配置、业务仓库里的任务、业务模型、历史候选和报告会保留。发布者维护源码并提交新的预构建版本，同事只刷新插件源。当前没有额外的本地管理页面。

**本版本验证的是原生插件安装和刷新机制。** 尚未验证所有客户端的“更新”按钮位置，也不承诺后台定时更新或旧会话热更新。支持的客户端可以通过自己的插件界面管理启用和卸载；没有相应入口时使用上面的已验证命令。

`main` 是更新通道；`v0.13.2` 是本次版本标签。跟随 `main` 才能持续收到新版本；固定到标签的安装只会保留对应版本。

### 从 v0.4 手动连接迁移

若之前通过源码目录或安装包运行过 `connect`，先在**原安装目录**执行下面的命令。workspace 和 `--codex` 参数保持与旧连接一致：

```bash
node dist/src/cli.js disconnect --workspace "/absolute/workspace" --apply
```

它只移除匹配的旧 MCP 连接和未修改的全局 Skill，保留业务项目记录。然后按本文安装原生插件，并设置相同的 workspace。出现自定义 Skill 或连接冲突时先核对，不要删除不相关的配置。业务仓库若还放有旧版 `.agents/skills/project-dev` 或 `.codex/config.toml` 连接，需要单独检查，避免重复加载。

## 给团队使用

1. 将本仓库的 README 链接发给同事，无需添加协作者。
2. 每人在自己的 Codex 添加同一个插件源、安装插件，在业务仓库直接使用“项目开发”；首次运行自动初始化。
3. 使用相同版本和真实需求验证，记录需要纠正实现思路、遗漏关联改动以及额外操作的情况。
4. 将已审查、有复用价值的规则放入业务仓库的 `.project-dev/knowledge/`，通过团队原有 Git 审查流程共享。

每个 Git 工作目录独立维护结构索引、业务模型、历史候选和任务记录；同一项目在不同同事电脑上的资料也分别积累，不会因使用同一个插件源而自动同步。团队需要共享的知识通过审查后的业务仓库文件维护。

同一 Codex 用户配置当前维护一份允许访问的工作范围，默认是首次接入的仓库。接入范围之外的项目时，需要明确切换范围，或将范围设置为包含多个仓库的父目录；范围内各项目的资料仍分别维护。

插件用户无需执行旧版 `connect` 或 `project init`；后者属于源码模式，会写入项目级 Skill 和 MCP 连接，可能造成重复加载。

当前桌面版的插件清单对原生钩子有加载差异。发布目录使用官方支持的 `.codex-plugin/plugin.json` 兼容入口，并显式声明 MCP 与钩子；仓库根 `plugin.json` 保留为维护元数据来源。打包脚本统一生成，安装与更新仍用原生插件机制。

## 技术实现与数据位置

| 组成 | 职责 |
| --- | --- |
| **Codex** | 理解需求、阅读源码、整理业务模型与历史习惯、判断影响范围、修改代码并执行验证。 |
| **Skill** | 指导执行顺序：开发前查询项目依据，实施时维护模型和关联清单，完成后检查验证结果并保留经验。 |
| **原生钩子与上下文提供器** | 会话与输入钩子提供项目入口；PreToolUse 检查支持的修改路径，PostToolUse 记录工具返回，Stop 有界收尾诊断。钩子须由宿主信任，异常与未就绪明确可见。 |
| **自研本地 MCP 服务** | 使用 TypeScript、Node.js 和 MCP SDK，通过 STDIO 提供 16 个工具，负责配置与初始化、结构扫描、上下文检索、业务模型与历史结果校验保存、任务检查及经验记录。 |
| **终端检查执行器** | 从已保存计划读取命令，在 Codex 原终端运行并生成真实结果；MCP 读取结果核对验收，不执行项目脚本。 |
| **项目本地记录** | 使用文件保存结构索引、业务模型、任务、候选和来源版本；无需部署独立后端。源码引用、文件哈希和修订号用于追溯与复核。 |

MCP 是 Codex 调用这些工具的接口。业务含义由当前 Codex 模型分析，MCP 服务执行扫描、检索、来源校验和保存操作；已有资料通过工具查询进入后续会话上下文，供 Codex 结合当前源码使用。

整体架构图见[团队演讲稿：整体架构](docs/team-introduction.html#overview)。演讲按“总览 → 模块拆解 → 开发落地 → 价值总结 → 后续规划”组织：先看定位、背景和架构，再讲各模块；随后用同一份 SDD 串起使用流程与前后对比，最后回到价值、边界及规划。

### MCP 的功能、目的与解决的问题

**目的：让项目上下文和交付依据成为可以反复查询、更新和检查的记录。** Skill 指导何时做这些事，Codex 负责语义分析、设计判断和代码修改，MCP 将可确定的数据操作与校验交给程序执行。当前插件的 16 个工具按以下五类组织，参数由 Agent 维护，用户不用逐个调用。

| 功能 | 对应工具 | 解决的问题 |
| --- | --- | --- |
| 接入、配置与范围校验 | `plugin_status`、`plugin_configure`、`project_prepare` | 核对版本、真实 Git 项目和允许范围，自动完成首次接入，减少接错项目或跨项目混用资料 |
| 结构扫描与上下文检索 | `project_scan`、`project_context`、`knowledge_search` | 定位规范、公共能力、相似模块、直接使用方和适用规则，帮助 Codex 先查现有实现再生码 |
| 业务模型维护 | `project_model_record`、`project_model_apply` | 校验来源、规则、关系和修订，保存模型并在核验后回写变更；避免把过期总结或未实现预期直接当作当前行为 |
| 历史、纠正与经验 | `history_scan`、`history_next`、`history_record`、`project_feedback_record`、`experience_propose` | 发现历史并分批供 Codex 分析，核验原话与范围，保存可修订、可停用的候选，减少反复解释 |
| 任务与交付核验 | `task_open`、`task_update`、`task_check` | 保存需求、实现依据、关联清单及验收，对照差异、代码指纹和真实检查结果核对完成条件，支持中断恢复 |

例如，新增模块要使用现有请求封装时，MCP 返回候选入口、真实用法及源码位置，Codex 阅读并选择复用方式，再通过工具保存依据与验收关系。结束时核对来源和检查结果是否仍有效。MCP 不能只靠检索命中就证明已复用，也不能自动判定设计正确。

这套服务使用 TypeScript、Node.js 和 MCP SDK，通过 STDIO 在本机与 Codex 通信；工具参数由 schema 校验，项目范围、原文、哈希、修订及任务条件由领域服务校验。各工具调用的结果与耗时还会进入统一诊断包装，用于维护者排查运行问题。源码入口为 [MCP 服务](src/server.ts)，具体业务实现分布在结构检索、业务模型、历史和任务等模块中。

MCP 不独立调用模型理解业务，不代替原终端执行项目检查，也不能拦截 Codex 绕过工具直接修改源码；模型语义、实现取舍与最终业务正确性仍需结合源码审查和实际验证。

```text
业务仓库/
└── .project-dev/
    ├── project.yaml         # 可选的项目配置
    ├── knowledge/           # 经审查、可通过业务仓库共享的知识
    └── local/               # Git 本地忽略的个人记录
        ├── tasks/           # 任务、清单、来源版本及验收修订
        ├── baselines/       # 接入时已有改动的内容快照
        ├── feedback/        # 本项目即时纠正、原话及修订链
        ├── requirements/    # 当前需求授权缓存的PRD片段与原型图片
        ├── understanding/   # 结构索引、业务模型及其修订版本、HTML 报告
        ├── validation/      # 实际检查的启动事实、退出码、日志摘要与快照
        ├── history/         # 项目历史文本缓存、候选与 HTML 报告
        └── proposals/       # 待审查的经验草稿
```

首次个人接入按需建立 `local/`，不会要求生成或提交整套共享配置。用于分析的源码和历史片段会进入当前 Codex 会话上下文；本地存储不代表完全离线分析。这些个人记录不会由工具自动上传到本 GitHub 仓库。

自动辅助的触发识别是轻量启发式，可能误判或漏判；普通对话、没有会话归属的“继续”和未信任的钩子不会被当成已跟踪开发。复杂项目在钩子预算内未完成查询时退回空上下文，明确调用仍可使用完整查询。

## 当前能力边界

- **关联分析是辅助线索。** 当前主要提取 JS/TS、Vue、Svelte 等代码中的直接导入关系，不是完整 AST、调用图或跨系统业务影响分析；动态调用和其他语言关系仍需人工与 Codex 核对。
- **历史分析有来源范围。** 只覆盖本机可读取且能够归属当前项目的 Codex 对话文本，不等于全员历史；历史附件正文暂不解析。
- **业务理解逐步积累。** 从代码观察到的行为不等于已确认产品规则，后端不可见逻辑和业务歧义仍需确认。
- **清单与验证记录不保证实现正确。** Skill 是执行指导，不是强制拦截机制；真实项目的测试与代码审查仍然需要。
- **项目资料在本机维护。** GitHub 用于分发工具版本，业务模型、历史和任务不上传到团队共享知识服务；诊断元数据按上述开关发送到维护者接收端。业务仓库及 Git 元数据必须位于配置的 workspace 内，范围外的 worktree 需要正确的目录配置。

## 常见问题

| 现象 | 处理方式 |
| --- | --- |
| GitHub 提示 Repository not found 或下载失败 | 检查是否使用本文完整的 HTTPS 地址，以及本机网络或代理能否访问 GitHub；本仓库无需邀请权限。 |
| 找不到 `codex` 或提示未知 `plugin` 命令 | 使用实际 Codex CLI 路径，并检查 Codex 版本是否支持原生插件命令。 |
| 项目使用 Node 18，旧说明要求升级到 20 | 更新插件到 v0.6.2 或更高版本，插件运行支持 Node 18.19.0+。保留业务项目的 Node 设置，重启 Codex 后确认工具可用。 |
| Skill 或 MCP 工具没有出现 | 确认原生插件已安装并启用，Node 与 Git 可用；重启 Codex 并新建对话，检查旧连接或项目级 Skill 是否重复。 |
| `PLUGIN_NOT_CONFIGURED` | 先使用“项目开发”，它会通过 `project_prepare` 自动初始化当前仓库；更新后仍遇到旧流程时，重启 Codex 并新建对话。 |
| 下载超时或 `early EOF`，仍停留旧版 | 使用上方带 `-c` 稀疏目录的更新命令。旧版更新 Skill 尚未包含修复，可先执行一次命令升级。重复失败时检查当前协议的网络连通性，不反复完整克隆或绕过 SSH 校验。 |
| 更新后仍显示旧运行版本 | 区分安装版本与当前进程版本；更新后重启 Codex 并新建对话。 |
| `PROJECT_OUTSIDE_WORKSPACE` | 检查当前业务仓库及其 Git 元数据是否位于配置的 workspace 内。 |
| 建任务仍返回 `WORKTREE_DIRTY` | 当前进程可能仍在用旧版本；更新到 0.11 后新建对话。新版会保存接入内容，未解决合并冲突仍须处理。 |
| `ACTIVE_TASK_EXISTS` | 先恢复当前仓库未完成的任务，确认是否与本次需求一致。 |
| `SKILL_CONFLICT` / `MCP_CONFIG_CONFLICT` | 比较已有配置和新版本，确认安装目录、Node 路径、workspace 与自定义修改；安装器不会覆盖不匹配内容。 |
| 首次扫描后没有业务模型 | 结构扫描只建立索引；通过具体需求或“梳理某模块业务模型”的请求，让 Codex 阅读源码后记录。 |
| 业务模型显示 `needs_review` | 查看具体待复核规则与关系，核对后局部修订；重扫不会清除旧规则状态。只有索引过期才需要先扫描。 |
| 模型只返回摘要 | 新版默认精简摘要；通过 `details_request` 读取详情，也可用 `rule_ids` 只读取相关规则、异常和依据。 |
| `IMPLEMENTATION_BASIS_REQUIRED` / `IMPLEMENTATION_BASIS_REVIEW_REQUIRED` | Codex 读取项目依据并保存本次实现选择，按当前代码逐项复核关联验收。晚补如实记录，用户无需填写表单。 |
| `PROJECT_REUSE_REQUIRED` / `PROJECT_REUSE_CONTEXT_REQUIRED` | Codex 核对既有请求入口和用法，优先改为复用；确需例外则在原清单记录源码依据和具体缺口。覆盖不足先刷新索引并补充检查。 |
| `VALIDATION_PLAN_REQUIRED` / `VALIDATION_RUN_REQUIRED` | Codex 保存当前检查计划并通过原终端执行；失败、未运行或过期时修复后重跑，不能手写通过记录。 |
| `BUSINESS_DELTA_PENDING` / `BUSINESS_DELTA_CONFLICT` | Codex 核对原规则、需求草案及场景验收，依据当前源码回写模型；规则已变化时重新读取并追加修订。 |
| `FEEDBACK_REVIEW_REQUIRED` | Agent 读取当前相关纠正，保存适用选择并重新核验关联验收。 |
| `REQUIREMENT_SOURCE_UNAVAILABLE` / `REQUIREMENT_ACCEPTANCE_REQUIRED` | 来源缺失、不可读或已变化，补齐原型/文档后重开并核验；测试通过不能代替。 |
| `ACCEPTANCE_REVISION_REQUIRED` | 验收含义或类别变化，记录需求修订原因并先保存 pending，保留旧定义。 |
| `BUSINESS_ASSESSMENT_REQUIRED` | Agent 明确业务影响；变化时绑定实际模型、草案与场景，未知继续待核实。 |
| `BUSINESS_CHECK_STALE` | 显式绑定的业务规则、依据或场景已变化；重新核对并修订对应验收，再完成审查。 |
| `REVIEW_STALE` / `REVIEW_SNAPSHOT_CHANGED` | 代码已变化或旧证据缺少指纹；重新核对受影响的审查与验证记录，再提交。不能只换指纹沿用旧结果。 |
| 历史习惯提取错了 | 告诉 Codex 具体错误，读取来源批次后修订或停用候选；原记录会归档，版本冲突时重新读取。 |
| 历史分析显示 `paused` | 剩余批次尚未分析，可以先开发；提出“继续历史分析”即可恢复。 |
| 历史读取失败但业务模型正常 | 综合查询会保留可用的业务模型，并单独标注历史不可用。根据诊断修复历史资料。 |
| `PLUGIN_SETTINGS_BUSY` | 确认已退出的进程遗留锁会自动恢复；仍存活或无法识别的持有者不会被强行解锁。 |
| 报告显示未覆盖或未完成 | 根据报告检查排除项、扫描限制或待分析批次，继续相关步骤，不把部分结果当作全量完成。 |

## 卸载插件

```bash
codex plugin remove project-dev-agent@project-dev-team
```

也可使用 Codex 插件界面的卸载入口。个人 workspace 设置和业务仓库里的任务、知识与报告位于插件缓存之外，会继续保留。重新安装可复用这些数据；如需删除数据，请先核对范围和备份。

## 开发与详细文档

开发工具本身时，使用 Node 20.19+，在本仓库执行：

```bash
npm ci --ignore-scripts
npm run check
```

`npm run check` 执行类型检查、源码构建、插件打包和自动化测试。只修改源码不会向同事发布新版；发布前需要统一修改 `package.json`、锁文件、`plugin.json` 和 `src/version.ts` 的版本，重新构建并提交 `plugins/project-dev-agent/`。完整发布步骤见 [插件发布与维护](docs/plugin-release.html)。

**每次发布同步维护说明。** README 与[团队演讲稿](docs/team-introduction.html)应一起核对版本、日期、整体架构、入口及默认模式、SDD 分工、业务模型、选型规则、诊断策略、验证证据和后续规划。已实现能力与规划分别说明；历史测试保留对应版本，不能挪用旧结果代表新版。演讲稿导出到仓库之外时同步更新副本；说明性更新不应伪造运行版本或验证结果。

发布前还需使用隔离的 Node 18.19.0 和 18.19.1 执行 `npm run test:runtime`（先在构建环境完成 `npm run check`），验证最低版本和反馈环境。该命令复用已构建产物，不重新安装源码依赖；测试覆盖真实 STDIO 调用、扫描、业务模型、历史记录和任务恢复。[兼容性工作流](.github/workflows/runtime-compatibility.yml) 会在推送和 PR 时执行上述版本矩阵。
