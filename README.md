# Project Dev Agent

**让 Codex 在改代码前了解项目惯例、业务背景和相关改动范围，并把开发中的纠正经验留给下一次任务。**

这是接入 Codex 的开发辅助插件，通过**项目结构扫描、业务建模、历史习惯整理和关联改动检查**，帮助 Codex 按当前项目的实际情况开发。适合已经用 Codex 修改项目、但仍需要反复纠正实现思路的开发者，可以用于不同业务项目。

当前版本：**v0.10.0，供个人使用和小范围团队验证**。通过公开的 GitHub 插件源分发原生 Codex 插件，运行代码和依赖已打包。同事无需克隆源码、运行 npm 或手动同步 Skill。

## 它能帮你做什么

| 能力 | 解决的问题 | 具体做法 |
| --- | --- | --- |
| **项目结构扫描** | 不熟悉项目组织方式与已有实现 | 建立文件、模块和静态引用索引，辅助 Codex 查找同类页面、公共组件和已有封装。 |
| **业务建模** | 每次都要重新解释业务背景 | 按业务能力整理术语、状态流程、逐条规则与异常；规则绑定依据，业务关系辅助发现关联入口，默认读摘要，按需读详情与局部修订。 |
| **历史习惯整理** | 已经纠正过的问题重复出现 | 分批分析本机项目对话，提取带用户原话的习惯候选；支持暂停续跑、纠正误提取和停用候选，保留旧版依据。 |
| **关联改动检查** | 只改当前文件，遗漏其他入口 | Codex 结合代码引用与业务关系建立“修改 / 验证”清单，工具对照 Git 变更检查覆盖与待处理项。 |
| **业务验证与效果统计** | 只验证正常路径，或无法判断实际收益 | 从规则整理正常、边界和异常验证建议，绑定现有验收；从本地任务统计纠正与验证现状，有真实同口径配对才比较。 |
| **任务与经验保留** | 换个对话就丢失进度或纠正原因 | 保存需求、验收、验证记录和纠正经验；证据绑定代码指纹，代码再次变化后需要重新核验。 |
| **默认生码规则** | 职责混杂、重复造组件、注释和用户要求遗漏 | 编码前明确模块与选型，编码中维护要求和注释，结束后按实际代码核对五项约束。 |

例如，修改一个订单状态的展示时，Agent 会先查找已有状态定义和展示组件，再核对列表、详情、筛选项及测试是否涉及这次变化。需要同步修改的地方和只需验证的地方都会进入清单；实际范围仍需结合当前代码判断。

## 新模块也要先遵循项目规范

**独立的是业务职责，公共基础设施继续复用。** 编码前先取得项目实现上下文，实际阅读适用规范、相似模块、公共入口及用法，再确定职责划分、设计方式和复用选择。新目录尚不存在时仍返回项目级线索；不能因局部查询没有命中，就认定项目没有既有封装。

从 **0.9.0** 起，这是一条所有开发任务共用的流程：

1. **先找依据**：定位适用规范、相似模块、共享实现与已有用法，新建目录也会提供项目级候选。Codex 实际阅读内容，再结合需求及已核实历史判断适用范围。
2. **作出实现选择**：用少量具体决策说明模块怎样分工、哪些已有方式应沿用、是否需要扩展或偏离以及原因。代码风格、注释、组件选型和用户要求按任务相关性纳入。
3. **接到原有验收**：Agent 自动记录真实原文引用与决策，每项关联现有验收项。MCP 核验路径、哈希、行文及关联关系，新任务缺失依据不能关闭。
4. **对照代码复核**：方案变化追加历史，相关验收先重新打开，保存后再检查；不能靠回传旧结论刷新证据。晚补依据会标明已有代码改动，不记成编码前准备。

请求库是复用问题的一个例子，职责划分、依赖边界、扩展方式与其他约定同样走该流程。原有 HTTP 静态检查继续保留，作为额外保护，不代表覆盖了所有设计问题。用户仍按原方式明确调用“项目开发”，无需增加命令或填写新表单。

**边界：** MCP 校验可核对的依据、记录与当前验收，无法拦截模型直接写文件，也不能凭真实引用证明它已理解代码或设计合理。未适用的旧习惯不强行沿用；语义与质量仍由 Codex 审查并结合项目验证。旧任务兼容保留，明确标为 `legacy`，不补造历史。

## 0.10：围绕真实开发的四项改进

开发入口仍是 `$project-dev 描述需求`，以下资料由 Agent 自动维护。

| 改进 | 如何帮助开发 | 实现与边界 |
| --- | --- | --- |
| **精准查找既有实现** | 新模块先找已有能力及真实用法，减少另起封装。 | 根据符号、命名词、标识符及路径排序，结合应用范围返回源码位置、当前指纹和直接使用方；新目录补充项目级候选。当前是本地词法检索，不是向量语义搜索，未命中需继续查代码。 |
| **业务规则变更预演** | 修改前看清“原规则 → 预期规则”，将正常、边界和异常场景接到验收。 | 草案保存在任务中，不覆盖现有模型。实现后核对源码、场景验收与实际检查，显式回写当前行为；保留回执，支持中断恢复和后续要求修订。是否符合业务仍需核实。 |
| **真实检查结果接入验收** | 避免仅凭一句“测试通过”就完成任务。 | 保存检查计划，由 Codex 原终端运行内部执行器，记录命令、退出码、日志摘要和前后代码指纹。生产代码缺少有效运行结果、失败、超时或过期时不能关闭新任务。 |
| **说明规则为什么适用** | 区分本次适用规则和相似线索，减少把旧习惯套进所有模块。 | 返回路径、模块、关键词的匹配理由及仍需核对的条件；候选、停用、过期及人工确认状态保持独立，命中不等于已经确认。 |

业务规则草案针对已建立的新格式模型；遇到未知业务，先阅读代码并建立有依据的模型。一个草案只改一条规则，保存原规则指纹，拒绝覆盖并发变化；不相关规则和旧证据保留。需求变化时追加后继草案，不改写已保存的历史。

检查命令由 Codex 按项目和需求选择，通过原有终端执行及权限流程运行，**MCP 不代替终端执行项目脚本**。执行器使用参数数组、限制时间及日志容量；不能靠 `task_update` 声明生成成功记录。新任务新增此约束，旧任务按 `legacy` 兼容；仅文档等修改可说明检查不适用。运行结果不证明测试覆盖充分或业务正确，本地记录也不防电脑文件所有者自行改写。

## 默认生码规则

从 v0.6.5 起，使用 `$project-dev` 开发时默认遵循下列规则。当前用户明确要求决定任务范围，具体实现结合项目现有约定；历史习惯和业务模型先核对适用条件。

| 规则 | 执行要求 |
| --- | --- |
| **按职责模块化** | 明确业务逻辑、数据访问、页面交互和通用工具的边界，禁止无关函数堆入同一文件。同一职责的辅助函数可以共置，只整理本次涉及的代码。 |
| **合理使用设计模式** | 根据实际变化点评估策略、状态、适配器等模式，并说明原因；简单逻辑保持简单，避免多余抽象。 |
| **保留用户要求** | 记录本次要求和验收项；新增或纠正要求时同步维护记录，结束时逐条核对。可复用要求保留来源、范围，候选不自动成为团队规则。 |
| **配套注释** | 模块说明职责，公共函数说明用途及必要契约，关键业务和复杂实现说明依据与原因；默认中文，修改逻辑时同步维护注释。 |
| **组件依次复用** | **项目已接入的组件库 → 项目已有可复用组件 → 自行实现**。核实实际 API、扩展能力及项目必要约束，进入下一层时说明上一层的不足。 |

编码前给出简短的职责划分与选择理由；实施时维护代码、注释和要求；结束时检查职责混杂、过度设计、需求遗漏、失效注释和重复实现。依据和审查结果写入现有任务清单、验收项和纠正记录，无需额外填写表单。无组件等不适用场景说明理由即可，小改动不强制生成设计文档。

**这些规则由 Skill 指导 Codex 执行。** MCP 继续提供 15 个工具，校验任务记录、证据和代码快照，新增任务还核验通用实现依据及关联验收，保留原有 HTTP 专项保护；模块边界、设计模式和注释的合理性仍由 Codex 审查，也不代替项目测试。详细示例见 [生码规则](skills/project-dev/references/generation-rules.md)。v0.10.0 保留任务、历史、设置及代码指纹规则；旧业务模型继续可读，按需核对后迁移为支持逐条依据的新模型。

## 几个核心概念

| 概念 | 含义 |
| --- | --- |
| **项目结构索引** | 记录文件在哪里、有哪些角色、哪些文件存在直接引用，用来定位需要阅读的代码。 |
| **业务模型** | 记录某个模块的业务含义、处理流程、规则职责及对应实现，帮助理解业务在当前代码中如何运行。 |
| **习惯候选** | 从用户历史表达和纠正中提取的开发偏好，带适用范围，需要结合当前需求和代码核对。 |
| **已确认项目知识** | 经过明确人工审查的项目规则；查询时还会检查来源是否有效。业务模型和习惯候选不会自动变成确认规则。 |
| **本次实现依据** | 本需求实际参考的原文、适用约束与实现选择；关联验收并保留修订历史，由 Agent 自动维护。 |
| **业务变更草案** | 本任务要变更的逐条业务规则，包含原规则、预期规则、需求依据及场景验收；通过核验后回写模型。 |
| **真实运行记录** | 终端执行器生成的检查命令、退出码、日志摘要和代码指纹，用于核对本次验收。 |
| **关联改动清单** | 针对本次需求列出的修改位置、验证位置、原因与证据，用来跟踪影响范围和完成情况。 |

## 中文使用说明

插件说明、操作提示、参数校验和报告分类使用中文。新生成的任务说明、业务模型、历史习惯候选与经验草稿默认使用简体中文；你明确指定其他语言时，会按你的要求生成。

命令、参数名、枚举值、错误码和代码标识保留原样。源码引用和历史原话逐字保留，已有记录不会为统一语言被批量改写。升级后重新生成的报告会使用中文分类，旧报告保留生成时的样子。第三方工具返回的原始错误可能保留英文详情。

## 安装前准备

- **Node.js 18.19.0+ 和 Git**，两者应能被 Codex 进程找到。插件已包含 JavaScript 依赖，但不包含 Node 本身。
- 已登录 Codex，CLI 支持 `codex plugin` 命令。如果提示未知命令，请先更新 Codex。
- 本机能够通过 HTTPS 访问 GitHub。下载本插件无需协作者邀请、GitHub 账号或 SSH 密钥。
- 一个已有提交的业务 Git 仓库，或包含多个 Git 仓库的工作目录。

无需额外模型 API Key、数据库或向量服务。语义分析使用当前 Codex 会话及其额度。

**业务项目使用 Node 18.19.1 可以直接运行插件，无需为了插件升级项目 Node。** 插件通过独立进程运行，不会修改业务项目的 `package.json`、`.nvmrc` 或全局 Node 配置。维护者从源码安装完整依赖、构建和发布工具时仍使用 Node 20.19+，这与同事使用预构建插件的要求不同。

## 首次安装：只做一次

插件列表中的三个入口使用中文名称和说明，调用命令保持不变：

| 入口名称 | 调用命令 | 用途 |
| --- | --- | --- |
| 项目开发 | `$project-dev` | 首次使用自动初始化，结合项目代码、业务背景和历史习惯开发需求。 |
| 项目设置 | `$project-dev-setup` | 查看配置或按需调整工作目录，日常使用无需单独执行。 |
| 插件更新 | `$project-dev-update` | 更新插件，保留工作目录配置和已有项目记录。 |

### 1. 添加插件源并安装

```bash
codex plugin marketplace add https://github.com/Clearlovesixteen/project-dev-agent.git --ref main
codex plugin add project-dev-agent@project-dev-team
```

第一条把公开 GitHub 仓库登记为插件源；第二条安装其中的插件。下载、版本缓存和启用状态由 Codex 管理。**不用把工具仓库克隆到自己的工作目录，也不用执行 npm install。**

仓库已公开，以上 HTTPS 地址可匿名下载。无需另外连接 GitHub 插件；使用本工具仍需正常登录 Codex。

如果终端找不到 `codex`，可以使用桌面应用内已有的 CLI 路径。部分 macOS 安装可执行：

```bash
"/Applications/ChatGPT.app/Contents/Resources/codex-cli/CodexCLI.app/Contents/MacOS/codex" plugin marketplace add https://github.com/Clearlovesixteen/project-dev-agent.git --ref main
"/Applications/ChatGPT.app/Contents/Resources/codex-cli/CodexCLI.app/Contents/MacOS/codex" plugin add project-dev-agent@project-dev-team
```

以实际安装位置为准；后文命令中的 `codex` 同样替换为这个路径。无需为安装修改全局 PATH。

### 2. 在项目中直接开始开发

安装后重新打开 Codex，在业务仓库新建对话，直接描述需求：

```text
$project-dev 帮我实现这个需求：……
```

**无需另外执行接入命令。** 首次开发会检测当前 Git 根目录，自动初始化该仓库，再继续结构扫描、历史整理和需求开发。已有配置时直接复用；重启或升级后不用重新接入。只查询状态时不会写入配置。

个人设置保存在 `${CODEX_HOME:-~/.codex}/project-dev-agent/settings.json`，独立于插件版本缓存。默认范围仅为首次使用的仓库；需要切换范围或使用包含多个仓库的父目录时，再使用可选的“项目设置”：

```text
$project-dev-setup 把工作目录设为 /absolute/workspace。
```

将占位路径替换为自己的现有绝对路径。当前目录无法识别、尚无 Git 提交，或仓库及 Git 元数据位于已配置范围之外时，会说明具体问题；不会自动扩大目录范围。

### 如何确认插件已生效（可选）

```text
$project-dev 接入当前项目，生成项目理解报告。
```

看到 `project_prepare`、`project_scan` 等实际工具调用和返回的报告路径，说明当前会话接入成功。只看到“已安装”说明安装完成，不等于当前对话已加载工具；工具未出现时，重新启动 Codex 并新建对话。

插件包含三个 Skill：日常开发 `project-dev`、可选设置 `project-dev-setup`、版本更新 `project-dev-update`。原生安装不会再向全局 Skill 目录手动复制文件。

## 第一次接入项目，会发生什么

安装插件后，在业务仓库首次使用 `$project-dev` 时开始接入；仅安装插件不会扫描所有项目。

1. **自动检测和初始化。** 定位当前 Git 仓库；未配置时保存该仓库作为工作范围，已配置时复用。在 Git 本地忽略规则中加入 `.project-dev/local/`，用于保存个人记录，不改变共享项目说明和业务代码。
2. **建立结构索引。** 扫描允许读取的源码和配置，识别目录、模块、页面入口、公共能力及直接导入关系，并报告已扫描、排除和未覆盖的范围。
3. **整理项目历史。** 查找本机 Codex 普通及归档会话中能够归属当前仓库的可见对话文本，分批分析并保存带用户原话的习惯候选。日常开发每轮默认最多分析 3 批，有剩余时保存断点并继续需求；后续对话接着处理。明确要求全量分析时持续处理。没有历史也可以继续使用。
4. **围绕需求建立业务模型。** 阅读实际涉及的模块，保存有用的术语、状态流程、业务规则、适用条件、异常和关联实现。每条规则绑定代码、文档或本项目已保存任务的依据，区分当前行为、预期行为与推断。记录由 Agent 维护，无需填写表单。

首次接入先建立结构基础，业务模型通过实际需求逐步补充。后续新开发对话会刷新结构索引；历史追加消息进入新批次，未变化的原批次继续保留分析、纠正和停用决定，日志归档也不会重置已有分析。原话或上下文被改写时需要重新分析。查询相关业务模型时，会核对其来源是否仍与当前源码一致。

历史分析由当前 Codex 会话执行。暂停后不会后台运行，也不会把剩余批次标为已完成；进度会说明已分析和待处理数量。用户主动暂停后，需要明确提出继续；因本轮预算暂停的，下个开发对话会从断点续跑。

结构扫描和历史整理可以在已有业务改动的仓库进行。**正式建立开发任务需要干净的 Git 基线**；已有改动由开发者决定如何保留或提交，工具不会自动 stash、reset 或 commit。

## 业务建模：可靠、精简、按需维护

**业务建模是核心能力。** Codex 负责阅读需求和代码、分析规则与业务关系；本地 MCP 校验引用、版本与条目关系，保存模型并提示需要复核的内容。同事仍然使用 `$project-dev` 描述需求，模型查询、记录和维护由 Agent 完成。

### 记录什么

| 内容 | 用途 |
| --- | --- |
| 业务对象与流程 | 按业务能力记录术语、状态含义和流程步骤，保留未知问题。 |
| 逐条业务规则 | 每条具有稳定 ID、职责、适用条件、异常条件和来源引用，避免只保存一段模糊总结。 |
| 规则性质 | 区分 **代码当前行为**、**需求预期行为**和**待核实推断**。当前实现与新需求不同，应识别差异并纳入开发及验收。 |
| 可核对的依据 | 源码与项目文档保留路径、行号、原文和哈希；本项目任务要求或纠正保留任务 ID、原文及哈希。 |
| 业务关系 | 记录规则实施位置、使用位置或依赖位置及理由；可引用已有模型复用公共概念，帮助发现没有直接代码导入的关联入口。 |
| 修订与待复核项 | 源码、任务纠正、规则内容或关联模型变化时，提示具体受影响的规则与关系；保留旧修订。 |

例如，新增“冻结”状态时，模型可以帮助分析编辑入口、详情展示、提交操作和接口校验是否受影响，并分别说明依据与未知内容。**这是用途示例；实际结论必须来自当前项目，不能把前端限制推断成后端已经校验。**

### 怎样保持精简

- **按需建模。** 首次先建立结构索引，围绕真实需求逐步积累，不要求先读懂全项目。
- **默认摘要。** 新版模型列表每页最多 5 个，先返回相关规则摘要；可按模型 ID、修订号和规则 ID 读取条件、异常、关系及依据。公共概念通过引用复用。
- **局部修订。** 已有新版模型使用 `patch` 按稳定 ID 更新或删除来源、规则、关系；未提交的条目和证据原样保留。单模型上限 64 KiB，超限按业务能力拆分。
- **减少打断。** Agent 自动维护资料，只有影响当前实现且无法从已有资料核实的关键业务歧义才询问。日常输出保持简短，详情按需查看。

### 怎样保持可靠

`project_scan` 刷新结构索引；`project_context` 查询并核对来源；`project_model_record` 校验并保存。模型内的来源、规则与关系使用稳定 ID，工具拒绝悬空引用、重复 ID、过期修订号和不匹配的原文。

**每条规则独立保存依据指纹。** 即使两条规则引用同一文件，也只刷新本次实际复核的规则。只换来源哈希、改摘要或重新扫描，不会把其他旧规则变成已核对。业务关系还跟踪其关联规则、目标文件及被引用模型修订号的变化。

`needs_rescan` 表示索引需要刷新，`needs_review` 表示业务内容需要重新阅读核对；查询结果给出待复核规则、关系及路径。复核由 Codex 在当前开发会话执行，随后提交局部修订；没有后台自动重写模型的进程。

模型及修订保存在当前项目的 `.project-dev/local/understanding/`，可选报告为该目录下的 `report.html`。报告是生成时快照，实时状态以工具查询为准。

**v0.6.5 及以前的模型继续可读。** Agent 仅在实际需要时读取旧模型，补齐规则依据、条件和异常，再迁移到新版；旧版本保留，不批量编造来源，也不允许用旧格式覆盖新版模型。无需同事手动迁移文件。

**模型始终是候选。** 引用匹配能证明来源存在，不能证明所有业务判断正确。业务关系只展开一层显式记录，不能保证发现全部调用或跨系统影响。记录预期行为也不表示用户已批准团队规则；共享知识仍通过原有明确审查流程确认。具体参数见 [业务建模输入说明](skills/project-dev/references/understanding-inputs.md)。

## 0.8 的六项改进

| 改进 | 开发时如何运行 |
| --- | --- |
| **规则分歧检查** | 比较范围、职责、条件及异常一致的结构化断言，返回相互矛盾或代码与需求不同的依据。Codex 核实后处理，关键未知才询问。没有断言的自然语言矛盾仍需阅读判断。 |
| **真实效果统计** | 收尾时自动读取本项目任务的纠正条目和当前验收、验证现状；没有真实同需求、同验收口径对照时明确显示数据不足，不报改善率。 |
| **关联检查补全** | 修改前结合计划路径，修改后结合实际差异，核对双向引用、共享标识符和显式业务关系中的相关入口。提示是核对线索，不表示所有位置都必须修改。 |
| **业务场景验收** | 根据规则条件和异常整理正常、边界和异常建议，适用场景绑定已有验收；显式绑定后，规则或依据过期会阻止沿用旧验收关闭任务。 |
| **重复识别与复用** | 识别明确重复的规则和同名术语差异，提示公共模型引用。由 Codex 核对含义并局部整理，保留来源和旧修订，不自动删除整份模型。 |
| **增量结构扫描** | 复用安全路径和文件元数据未变化的结构记录，显示实际读取与复用数量；新增、删除与别名关系仍刷新。业务依据查询继续核对真实源码。 |

这些改进仍由“项目开发”处理，无需同事添加命令、管理页面或填写质量表单。新字段为可选，旧模型和旧任务继续可读，旧规则不会仅因升级而失效。模型查询、影响分析和场景建议都有容量限制，会明确返回截断情况。

效果统计记录的是**当前已保存事实**：纠正条目数不等于交互次数，当前失败记录数不等于历史失败总次数，也不能推算返工工时。维护者明确安排对照时，可选标注真实 baseline/assisted 样本；夹具、重复分组、不同验收口径、未完成或截断样本不产生真实改善结论。

## 日常怎么用

在 Codex 中调用 `$project-dev`，后面直接描述需求，不需要每次复制一大段固定提示词。

| 你想做什么 | 可以这样说 |
| --- | --- |
| 实现需求 | `$project-dev 帮我实现这个需求：……` |
| 根据 PRD 开发 | `$project-dev 根据这份 PRD 实现需求，先梳理验收项和关联改动范围。` |
| 梳理业务模型 | `$project-dev 整理订单模块的业务模型，保存术语、流程和规则职责，列出源码依据与待确认问题。` |
| 复用业务模型 | `$project-dev 基于已有业务模型分析这次需求的影响范围，先核对相关源码是否变化。` |
| 继续上次任务 | `$project-dev 继续当前仓库上次未完成的任务。` |
| 查看历史习惯 | `$project-dev 分析当前项目的历史习惯，给我查看报告。` |
| 暂停或继续历史分析 | `$project-dev 先暂停历史分析，继续当前需求。` / `$project-dev 继续分析剩余历史。` |
| 纠正误提取的习惯 | `$project-dev “所有页面用原生表单”理解错了，只适用于旧订单页面，请核对原话后修订。` |
| 停用习惯候选 | `$project-dev 停用这条误提取的习惯，保留修订记录。` |
| 纠正实现方式 | `这里应该复用现有封装，另外两个入口也要同步处理，原因是……` |

PRD 需要以当前 Codex 会话可读取的文本或附件提供。附件解析由 Codex 负责；本工具不提供独立的 Word、PDF 或图片解析服务。

习惯修订会保留旧版本，重新扫描不会覆盖未变化批次的修订结果。一个候选可能来自多个批次，Codex 会核对各批次；停用候选不会自动撤销已人工确认的共享知识，后者需要单独审查。

审查或执行验证前，Codex 通过 `task_check` 获取代码指纹，核验后将同一指纹随证据提交。重新核验已有完成项时，还会通过 `reviewed_ids` 明确本次复核的条目；只检查 A，不会让完整列表中 B 的旧证据一起刷新。代码再次变化时，旧证据标为待复核，并阻止直接关闭任务。该机制不代替实际测试，指纹不包含被 Git 忽略的依赖及外部服务状态。

从 v0.6.3 或更早版本升级后，活跃任务的旧证据需要重新核验一次，防止沿用旧版可能误刷新的记录；已结束的历史任务保留。工具和 Skill 会提示 Codex 如何逐项完成，开发者无需手写这些参数。

一个需求通常按下面的顺序推进：

```text
理解需求与验收标准
  → 查询项目结构、业务模型、历史候选与已确认知识
  → 阅读源码，核对业务关系，按需补充模型和关联改动清单
  → 明确模块职责、设计选择与复用依据，保存业务变更草案及检查计划
  → 修改代码并维护注释，记录新增要求和纠正原因
  → 审查适用生码规则，通过原终端执行检查，逐项完成业务场景验收
  → 按实际源码回写业务规则，核对执行结果，保存任务结果和经验候选
```

习惯和业务理解的候选需要结合当前代码核对。候选不会自动变成团队规则；确认共享知识需要显式审查。

## 更新到最新版本

在 Codex 里说：

```text
$project-dev-update 更新 Project Dev Agent 到最新版。
```

它会调用 Codex 原生插件管理器刷新配置好的插件源，并核对安装版本。也可以直接执行：

```bash
codex plugin marketplace upgrade project-dev-team
codex plugin list --marketplace project-dev-team --json
```

已实测：刷新 Git 插件源会更新已启用插件的版本缓存。更新后**新建对话或重启 Codex**，使 MCP 进程和 Skill 加载新版；运行中的旧对话不会自动切换。更新前先完成或保存当前开发任务。

工作目录配置、业务仓库里的任务、业务模型、历史候选和报告会保留。发布者维护源码并提交新的预构建版本，同事只刷新插件源。当前没有额外的本地管理页面。

**本版本验证的是原生插件安装和刷新机制。** 尚未验证所有客户端的“更新”按钮位置，也不承诺后台定时更新或旧会话热更新。支持的客户端可以通过自己的插件界面管理启用和卸载；没有相应入口时使用上面的已验证命令。

`main` 是更新通道；`v0.10.0` 是本次版本标签。跟随 `main` 才能持续收到新版本；固定到标签的安装只会保留对应版本。

### 从 v0.4 手动连接迁移

若之前通过源码目录或安装包运行过 `connect`，先在**原安装目录**执行下面的命令。workspace 和 `--codex` 参数保持与旧连接一致：

```bash
node dist/src/cli.js disconnect --workspace "/absolute/workspace" --apply
```

它只移除匹配的旧 MCP 连接和未修改的全局 Skill，保留业务项目记录。然后按本文安装原生插件，并设置相同的 workspace。出现自定义 Skill 或连接冲突时先核对，不要删除不相关的配置。业务仓库若还放有旧版 `.agents/skills/project-dev` 或 `.codex/config.toml` 连接，需要单独检查，避免重复加载。

## 给团队使用

1. 将本仓库的 README 链接发给同事，无需添加协作者。
2. 每人在自己的 Codex 添加同一个插件源、安装插件，在业务仓库直接使用“项目开发”；首次运行自动初始化。
3. 使用相同版本和真实需求验证，记录需要纠正实现思路、遗漏关联改动以及额外操作的情况。
4. 将已审查、有复用价值的规则放入业务仓库的 `.project-dev/knowledge/`，通过团队原有 Git 审查流程共享。

每个 Git 工作目录独立维护结构索引、业务模型、历史候选和任务记录；同一项目在不同同事电脑上的资料也分别积累，不会因使用同一个插件源而自动同步。团队需要共享的知识通过审查后的业务仓库文件维护。

同一 Codex 用户配置当前维护一份允许访问的工作范围，默认是首次接入的仓库。接入范围之外的项目时，需要明确切换范围，或将范围设置为包含多个仓库的父目录；范围内各项目的资料仍分别维护。

插件用户无需执行旧版 `connect` 或 `project init`；后者属于源码模式，会写入项目级 Skill 和 MCP 连接，可能造成重复加载。

## 技术实现与数据位置

| 组成 | 职责 |
| --- | --- |
| **Codex** | 理解需求、阅读源码、整理业务模型与历史习惯、判断影响范围、修改代码并执行验证。 |
| **Skill** | 指导执行顺序：开发前查询项目依据，实施时维护模型和关联清单，完成后检查验证结果并保留经验。 |
| **自研本地 MCP 服务** | 使用 TypeScript、Node.js 和 MCP SDK，通过 STDIO 提供 15 个工具，负责配置与初始化、结构扫描、上下文检索、业务模型与历史结果校验保存、任务检查及经验记录。 |
| **终端检查执行器** | 从已保存计划读取命令，在 Codex 原终端运行并生成真实结果；MCP 读取结果核对验收，不执行项目脚本。 |
| **项目本地记录** | 使用文件保存结构索引、业务模型、任务、候选和来源版本；无需部署独立后端。源码引用、文件哈希和修订号用于追溯与复核。 |

MCP 是 Codex 调用这些工具的接口。业务含义由当前 Codex 模型分析，MCP 服务执行扫描、检索、来源校验和保存操作；已有资料通过工具查询进入后续会话上下文，供 Codex 结合当前源码使用。

```text
业务仓库/
└── .project-dev/
    ├── project.yaml         # 可选的项目配置
    ├── knowledge/           # 经审查、可通过业务仓库共享的知识
    └── local/               # Git 本地忽略的个人记录
        ├── tasks/           # 任务、清单与验证证据
        ├── understanding/   # 结构索引、业务模型及其修订版本、HTML 报告
        ├── validation/      # 实际检查的启动事实、退出码、日志摘要与快照
        ├── history/         # 项目历史文本缓存、候选与 HTML 报告
        └── proposals/       # 待审查的经验草稿
```

首次个人接入按需建立 `local/`，不会要求生成或提交整套共享配置。用于分析的源码和历史片段会进入当前 Codex 会话上下文；本地存储不代表完全离线分析。这些个人记录不会由工具自动上传到本 GitHub 仓库。

## 当前能力边界

- **关联分析是辅助线索。** 当前主要提取 JS/TS、Vue、Svelte 等代码中的直接导入关系，不是完整 AST、调用图或跨系统业务影响分析；动态调用和其他语言关系仍需人工与 Codex 核对。
- **历史分析有来源范围。** 只覆盖本机可读取且能够归属当前项目的 Codex 对话文本，不等于全员历史；历史附件正文暂不解析。
- **业务理解逐步积累。** 从代码观察到的行为不等于已确认产品规则，后端不可见逻辑和业务歧义仍需确认。
- **清单与验证记录不保证实现正确。** Skill 是执行指导，不是强制拦截机制；真实项目的测试与代码审查仍然需要。
- **插件在本机运行。** GitHub 用于分发工具版本，没有团队中央数据服务。业务仓库及 Git 元数据必须位于配置的 workspace 内，范围外的 worktree 需要正确的目录配置。

v0.10.0 在 Node **18.19.0、18.19.1 和 20.19.6** 上逐版本通过全部 **222 项测试**，类型检查和三个 Skill 格式校验通过。覆盖精准检索与范围解释、业务草案与来源失效、真实检查与关闭保护、并发运行和中断恢复，以及实际发布运行文件的“草案 → 终端测试 → 场景验收 → 回写模型 → 重启关闭”闭环。另在 Node 18.19.1 完成已发布 **0.9.0 → 0.10.0** 的隔离原生升级，保留旧任务、设置、模型、历史修订与快照，测试运行文件哈希与发布包一致。结果见 [v0.10.0 验证数据](evals/results/plugin-v0.10.0-2026-10-23.json)；历史记录见 [v0.9.0](evals/results/plugin-v0.9.0-2026-10-23.json) 和 [验证记录](docs/verification.html)。

上述验证覆盖工具机制与发布流程，尚未取得同需求、同验收口径的独立模型前后对照；不能由测试数推断实际生码质量、返工或遗漏的改善幅度。真实遵循项目习惯的效果，仍需在更新后的开发会话中结合实际代码核对。

## 常见问题

| 现象 | 处理方式 |
| --- | --- |
| GitHub 提示 Repository not found 或下载失败 | 检查是否使用本文完整的 HTTPS 地址，以及本机网络或代理能否访问 GitHub；本仓库无需邀请权限。 |
| 找不到 `codex` 或提示未知 `plugin` 命令 | 使用实际 Codex CLI 路径，并检查 Codex 版本是否支持原生插件命令。 |
| 项目使用 Node 18，旧说明要求升级到 20 | 更新插件到 v0.6.2 或更高版本，插件运行支持 Node 18.19.0+。保留业务项目的 Node 设置，重启 Codex 后确认工具可用。 |
| Skill 或 MCP 工具没有出现 | 确认原生插件已安装并启用，Node 与 Git 可用；重启 Codex 并新建对话，检查旧连接或项目级 Skill 是否重复。 |
| `PLUGIN_NOT_CONFIGURED` | 先使用“项目开发”，它会通过 `project_prepare` 自动初始化当前仓库；更新后仍遇到旧流程时，重启 Codex 并新建对话。 |
| 更新后仍显示旧运行版本 | 区分安装版本与当前进程版本；更新后重启 Codex 并新建对话。 |
| `PROJECT_OUTSIDE_WORKSPACE` | 检查当前业务仓库及其 Git 元数据是否位于配置的 workspace 内。 |
| `WORKTREE_DIRTY` | 保留已有改动，由开发者处理后再建立任务；不要为了通过检查而丢弃代码。 |
| `ACTIVE_TASK_EXISTS` | 先恢复当前仓库未完成的任务，确认是否与本次需求一致。 |
| `SKILL_CONFLICT` / `MCP_CONFIG_CONFLICT` | 比较已有配置和新版本，确认安装目录、Node 路径、workspace 与自定义修改；安装器不会覆盖不匹配内容。 |
| 首次扫描后没有业务模型 | 结构扫描只建立索引；通过具体需求或“梳理某模块业务模型”的请求，让 Codex 阅读源码后记录。 |
| 业务模型显示 `needs_review` | 查看具体待复核规则与关系，核对后局部修订；重扫不会清除旧规则状态。只有索引过期才需要先扫描。 |
| 模型只返回摘要 | 新版默认精简摘要；通过 `details_request` 读取详情，也可用 `rule_ids` 只读取相关规则、异常和依据。 |
| `IMPLEMENTATION_BASIS_REQUIRED` / `IMPLEMENTATION_BASIS_REVIEW_REQUIRED` | Codex 读取项目依据并保存本次实现选择，按当前代码逐项复核关联验收。晚补如实记录，用户无需填写表单。 |
| `PROJECT_REUSE_REQUIRED` / `PROJECT_REUSE_CONTEXT_REQUIRED` | Codex 核对既有请求入口和用法，优先改为复用；确需例外则在原清单记录源码依据和具体缺口。覆盖不足先刷新索引并补充检查。 |
| `VALIDATION_PLAN_REQUIRED` / `VALIDATION_RUN_REQUIRED` | Codex 保存当前检查计划并通过原终端执行；失败、未运行或过期时修复后重跑，不能手写通过记录。 |
| `BUSINESS_DELTA_PENDING` / `BUSINESS_DELTA_CONFLICT` | Codex 核对原规则、需求草案及场景验收，依据当前源码回写模型；规则已变化时重新读取并追加修订。 |
| `BUSINESS_CHECK_STALE` | 显式绑定的业务规则、依据或场景已变化；重新核对并修订对应验收，再完成审查。 |
| `REVIEW_STALE` / `REVIEW_SNAPSHOT_CHANGED` | 代码已变化或旧证据缺少指纹；重新核对受影响的审查与验证记录，再提交。不能只换指纹沿用旧结果。 |
| 历史习惯提取错了 | 告诉 Codex 具体错误，读取来源批次后修订或停用候选；原记录会归档，版本冲突时重新读取。 |
| 历史分析显示 `paused` | 剩余批次尚未分析，可以先开发；提出“继续历史分析”即可恢复。 |
| 历史读取失败但业务模型正常 | 综合查询会保留可用的业务模型，并单独标注历史不可用。根据诊断修复历史资料。 |
| `PLUGIN_SETTINGS_BUSY` | 确认已退出的进程遗留锁会自动恢复；仍存活或无法识别的持有者不会被强行解锁。 |
| 报告显示未覆盖或未完成 | 根据报告检查排除项、扫描限制或待分析批次，继续相关步骤，不把部分结果当作全量完成。 |

## 卸载插件

```bash
codex plugin remove project-dev-agent@project-dev-team
```

也可使用 Codex 插件界面的卸载入口。个人 workspace 设置和业务仓库里的任务、知识与报告位于插件缓存之外，会继续保留。重新安装可复用这些数据；如需删除数据，请先核对范围和备份。

## 开发与详细文档

开发工具本身时，使用 Node 20.19+，在本仓库执行：

```bash
npm ci --ignore-scripts
npm run check
```

`npm run check` 执行类型检查、源码构建、插件打包和自动化测试。只修改源码不会向同事发布新版；发布前需要统一修改 `package.json`、锁文件、`plugin.json` 和 `src/version.ts` 的版本，重新构建并提交 `plugins/project-dev-agent/`。完整发布步骤见 [插件发布与维护](docs/plugin-release.html)。

发布前还需使用隔离的 Node 18.19.0 和 18.19.1 执行 `npm run test:runtime`（先在构建环境完成 `npm run check`），验证最低版本和反馈环境。该命令复用已构建产物，不重新安装源码依赖；测试覆盖真实 STDIO 调用、扫描、业务模型、历史记录和任务恢复。[兼容性工作流](.github/workflows/runtime-compatibility.yml) 会在推送和 PR 时执行上述版本矩阵。
